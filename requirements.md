# Requirements

Document vivant décrivant le besoin, les choix d'architecture, le périmètre de la v0 et le reste à faire. À tenir à jour au fil des décisions. Les récits de débogage déjà refermés et les propositions abandonnées sont archivés dans `requirements-archive.md` (pointeurs « cf. archive » ci-dessous) plutôt que gardés ici en entier, pour que ce fichier reste concentré sur l'architecture actuelle.

## Besoin

**Objectif** : étendre la simulation de systèmes physiques dans OpenModelica en y intégrant la simulation de l'exécution de programmes informatiques (logiciel embarqué). Il s'agit de fournir, sous forme de bibliothèque OpenModelica, un modèle de microcontrôleur programmable, dont le comportement est piloté par un script Python écrit par l'utilisateur et **compatible avec MicroPython**.

**Pourquoi** : cela permet de modéliser des systèmes complexes couplant matériel et logiciel — de programmer une « intelligence » (logique de pilotage) qui contrôle un système physique simulé, et de la tester numériquement avant tout passage sur un prototype réel.

**Public visé / cas d'usage** :
- Pédagogique (Lycée Jules Haag) : les élèves testent leur code de pilotage sur le système numérique avant de le déployer sur le prototype physique.
- Industriel : même logique de jumeau numérique pour valider un logiciel embarqué avant déploiement sur matériel réel.

**Contrainte clé** : le script Python écrit par l'utilisateur pour piloter le microcontrôleur simulé doit rester compatible avec MicroPython, afin d'être directement portable vers un microcontrôleur physique.

**Carte cible de référence** : Raspberry Pi Pico (RP2040). L'API `machine`/`time` exposée par le modèle simulé doit coller à ce portage MicroPython précis plutôt qu'à une API générique, pour rester fidèle à une carte réelle et garantir la portabilité du code.

**Contrainte de synchronisation temporelle** : l'exécution du script Python doit rester synchrone avec la durée des steps de simulation Modelica (le temps simulé et l'avancement du script ne doivent pas diverger). Les attentes du script (`sleep`) doivent être « condensées » : si le script attend 1 heure, la simulation ne doit pas avoir besoin d'exécuter réellement 1 heure de temps de calcul pour l'y amener — le temps d'attente doit pouvoir être avancé virtuellement plutôt qu'exécuté pas à pas.

### Décision : Mécanisme d'exécution du script Python pendant la simulation

- **Choix retenu** : CPython embarqué (via l'API C de Python) dans un thread du process de simulation, appelé depuis Modelica via l'interface *External Object* d'OpenModelica. Un shim Python (`machine`, `time`, ...) imite l'API MicroPython du Raspberry Pi Pico (RP2040). `time.sleep(x)` est intercepté : le thread se bloque sur une condition variable en publiant « réveil demandé à t+x » ; à chaque step de communication, le solveur Modelica lit cette demande et, s'il n'y a rien d'autre à observer entre-temps, avance directement son temps simulé jusqu'à ce point (traitement en événement discret) avant de réveiller le thread. Les GPIO forment un état partagé lu/écrit des deux côtés à chaque step.
- **Alternatives envisagées** :
  - Vrai MicroPython embarqué (port *unix*), avec un module natif `machine` réécrit pour dialoguer avec le modèle Modelica — avantage : fidélité maximale, c'est littéralement MicroPython ; inconvénient : intégration plus lourde (compiler/embarquer le port, écrire un module C dédié). Gardée comme piste de repli.
  - Process Python séparé communiquant via FMI/IPC (socket, pipe, FMU) — avantage : découplage propre, portable vers d'autres outils compatibles FMI ; inconvénient : latence d'IPC et contrôle plus grossier du pas de temps, ce qui complique la compression fine des `sleep`.
- **Notes pour plus tard** : le shim `machine`/`time` devra être confronté à la documentation officielle MicroPython RP2040 pour limiter les écarts de comportement avec le vrai MicroPython. Si des tests (notamment avec les élèves) révèlent des incompatibilités bloquantes, envisager de migrer vers l'alternative « vrai MicroPython embarqué ».

**Implémenté (jalons M0-M9)** : CPython initialisé via l'API moderne `PyConfig`/`Py_InitializeFromConfig` (pas `Py_SetPythonHome`, dépréciée et peu fiable avec une distribution « embeddable » — cf. décision « Distribution Python embarquée » ci-dessous). Protocole de synchronisation thread worker ↔ Modelica : section critique (`CRITICAL_SECTION`) + condition variable (`CONDITION_VARIABLE`, API Windows), ping-pong strict (un seul thread actif à la fois) ; le worker acquiert le GIL une seule fois à son démarrage et le garde toute sa durée de vie (un seul thread Python actif, jamais de rappel concurrent). `PyRuntime_destroy` ne joint pas proprement le thread ni n'appelle `Py_FinalizeEx` (chaque simulation tourne dans un process OS séparé, récupéré par l'OS à la fin — cf. Restrictions v0). La fonction `PyRuntime_sync` draine elle-même, via une boucle interne, tous les réveils immédiats chaînés au même instant simulé (plusieurs `Pin` construits/pilotés sans `sleep` entre deux) plutôt que de compter sur l'itération d'événements de Modelica pour la rappeler assez de fois — historique des deux bugs qui ont mené à cette conception (réveil prématuré, puis blocage silencieux au-delà de 2-3 réveils chaînés) : cf. `requirements-archive.md`.

### Décision : Conception du shim `machine`/`time` (v0)

- **Choix retenu** :
  - Module `time` : `sleep(s)`, `sleep_ms(ms)`, `sleep_us(us)`, `ticks_ms()`, `ticks_us()`, `ticks_diff(a, b)` — toutes basées sur l'horloge simulée partagée (celle avancée par le mécanisme de compression des `sleep`), jamais sur l'horloge système, pour rester cohérentes avec la synchronisation temps script / temps de simulation.
  - Module `machine` : classe `Pin(id, mode=Pin.OUT, pull=None)`, avec les constantes `Pin.IN`, `Pin.OUT`, `Pin.PULL_UP`, `Pin.PULL_DOWN` et les méthodes `.value([x])`, `.on()`, `.off()` — repris tel quel de l'API `machine.Pin` de MicroPython sur RP2040. Aucune autre classe `machine.*` en v0 (cohérent avec la restriction GPIO simples ci-dessous).
  - Numérotation des GPIO alignée sur celle du Raspberry Pi Pico (`GP0` à `GP28`), pour que le code reste portable tel quel.
  - État partagé : chaque `Pin` lit/écrit une structure protégée par la même primitive de synchronisation que les `sleep` ; côté Modelica, cet état est exposé comme des connecteurs booléens indexés par numéro de GPIO, lus/écrits à chaque step de communication.
- **Alternatives envisagées** :
  - Exposer dès la v0 un `Pin` « riche » avec toutes les méthodes RP2040 (dont `irq()`) — écarté : hors périmètre de la v0 (restriction GPIO simples).
  - Définir des noms de fonctions maison plutôt que de coller à l'API MicroPython existante — écarté : casserait la contrainte de portabilité du code vers un microcontrôleur réel.
- **Notes pour plus tard** : étendre le shim avec ADC/PWM/Timer/I2C/SPI/UART au fur et à mesure (cf. TODO), en gardant le même principe (état partagé, synchronisé au step de communication, API calquée sur MicroPython RP2040). **Mise à jour (fait)** : le shim vit désormais dans un vrai fichier `.py` de la bibliothèque (`Resources/Scripts/_shim/machine_time_shim.py`) et non plus dans la chaîne C échappée `SHIM_BOOTSTRAP` — le miroir `docs/shim/machine_time_shim.py`, qu'il fallait resynchroniser à la main, est supprimé. Détail dans la décision « Emplacement du shim `machine`/`time` » ci-dessous.

**Implémenté et validé (jalons M4-M9)** : conforme au choix ci-dessus. Précisions :
- Le module `machine`/`time` est défini en Python (un fichier « bootstrap » exécuté une fois à l'initialisation, cf. décision « Emplacement du shim » ci-dessous), au-dessus d'un petit module natif C (`_pyruntime_native`) qui expose seulement `pin_init`/`pin_write`/`pin_read`/`sleep`/`ticks_ms` — approche hybride qui limite la quantité de code C nécessaire (pas de `PyTypeObject` fait main pour `Pin`).
- `pull` (paramètre du constructeur `Pin`) est accepté pour compatibilité de signature avec l'API MicroPython mais **n'a aucun effet électrique en v0** (pas de résistance de tirage modélisée) — limitation à documenter, cf. Restrictions v0.
- **Raffinement du principe « tout appel au shim est un point de synchro »** : en pratique, seuls `Pin.__init__`/`.value()`/`.on()`/`.off()` et `time.sleep*` déclenchent réellement un point de synchro (rendent la main à Modelica). `time.ticks_ms()`/`ticks_us()` ne synchronisent **pas** — ce sont de simples lectures de l'horloge déjà connue (`sim_time`, maintenue à jour à chaque synchro), et les faire yielder aurait rendu coûteuse une boucle de polling non bloquante typique (`while ticks_diff(...) < ...`). Le principe reste valable pour sa fonction première (garantir qu'une boucle sans `sleep()` mais avec lecture/écriture de broches reste interruptible) ; `ticks_diff` est une fonction Python pure (soustraction), pas besoin de la router vers le natif.
- **Extensions ajoutées après coup** : constante `Pin.LED = 25` (alignée sur `LED_PIN_ID` côté C, cf. décision « LED embarquée ») pour éviter le nombre magique `25` dans les scripts ; support de `Pin("LED", ...)` en plus de `Pin(25, ...)`/`Pin(Pin.LED, ...)`, comme sur le vrai Raspberry Pi Pico W — la traduction de la chaîne `"LED"` se fait entièrement dans `Pin.__init__` côté shim Python, avant tout appel natif, donc **sans aucun changement côté C** (`resolve_pin_index`/le parsing `PyArg_ParseTuple` ne voient jamais que des entiers). Méthode `Pin.toggle()` ajoutée, implémentée en Python pur au-dessus de `value()` déjà existant (`self.value(0 if self.value() else 1)`), sans nouvel appel natif.

### Décision : Emplacement du shim `machine`/`time` (fichier `.py` de la bibliothèque)

- **Contexte** : le shim était une chaîne C échappée (`SHIM_BOOTSTRAP`, ~150 lignes de Python entre guillemets dans `PyRuntimeImpl.c`), doublée d'un miroir lisible `docs/shim/machine_time_shim.py` à resynchroniser **à la main** à chaque changement — deux copies d'une même vérité, donc une dérive possible à chaque évolution du shim (`Display`, `UART`, `Timer`...).
- **Choix retenu** : le shim est un vrai fichier Python de la bibliothèque, `Resources/Scripts/_shim/machine_time_shim.py`, source unique éditable et lintable comme du vrai Python. Son chemin est un nouveau paramètre `shimPath` du constructeur `Internal.PyRuntime`, résolu côté `MCU.mo` par `Modelica.Utilities.Files.loadResource` — exactement le schéma déjà en place pour `scriptPath`/`pythonHome`/`libraryPath`. Côté C, `PyRuntime_new` le lit puis l'exécute par `PyRun_SimpleString`, via un helper `read_text_file()` **partagé avec le chargement du script utilisateur** (le thread worker faisait déjà ce `fopen`/`fread`/`PyRun_SimpleString` : le motif est factorisé plutôt que dupliqué). Une lecture impossible remonte un `ModelicaFormatError` explicite : sans shim, le runtime est inutilisable, il n'y a pas de dégradation gracieuse à offrir.
- **Alternatives envisagées** :
  - Garder la chaîne C et continuer de resynchroniser le miroir — statu quo, rejeté : le coût d'entretien se paie à chaque ajout de périphérique, et une dérive silencieuse entre les deux copies est invisible tant qu'on ne les diffe pas.
  - Générer la chaîne C depuis le `.py` à un moment du build — supprimerait la dérive sans ajouter de fichier lu à l'exécution, mais introduirait une étape de build dans un projet qui n'en a aucune (cf. `CLAUDE.md`), pour un bénéfice identique.
- **Notes pour plus tard** : le shim est désormais un fichier de ressources comme un autre — s'il venait à être déplacé, penser au `loadResource` de `MCU.mo`. Le dossier `_shim/` est un sous-dossier de `Resources/Scripts/`, donc il n'est pas ajouté à `sys.path` par `addScriptDirToPath` : le shim n'est pas importable comme un module par un script utilisateur, il est seulement exécuté par le runtime, ce qui est le comportement voulu.

### Décision : Interface GPIO côté Modelica (connecteurs et fréquence de synchro)

- **Choix retenu (mis à jour — voir « Implémenté et validé » ci-dessous pour la version finale)** :
  - Trois sources déclenchent un point de synchro (appel à `PyRuntime_sync`) : (1) le réveil d'un `sleep`, (2) un tick périodique minimal (période configurable, pour garder les écritures de sortie fraîches même si le script ne dort jamais), et (3) un `when` déclenché sur **toute transition d'une broche d'entrée** — ainsi aucun changement d'état en entrée ne peut se produire sans que le script soit sollicité, sans pour autant accrocher la synchro aux évaluations internes du solveur (essais d'intégration, itérations de Newton, etc., qui n'ont pas de sens physique garanti et casseraient la compression des `sleep`). C'est Modelica lui-même, via son mécanisme d'événements (`when`/franchissement de seuil), qui détecte ces transitions de façon fiable et peu coûteuse. **Ce point (déclencheurs de synchro) reste valable tel quel dans l'implémentation finale.**
  - ~~Chaque broche GPIO du modèle expose un connecteur de type `Modelica.Electrical.Digital`...~~ **Abandonné, cf. décision « Domaine électrique vs logique pur » ci-dessous** : ce choix initial supposait que le microcontrôleur ne s'intégrerait qu'à des circuits logiques abstraits. Une remarque en cours de session a rappelé que le besoin réel implique de vrais circuits électriques (LED+résistance, moteur, capteur...), incompatibles avec le domaine purement logique de `Modelica.Electrical.Digital` (pas de tension/courant réels). Remplacé par un pont électrique réel dans le domaine `Modelica.Electrical.Analog`.
- **Alternatives envisagées** :
  - Paire de connecteurs causaux `BooleanInput`/`BooleanOutput` par broche, à choisir manuellement selon le câblage — écartée : ne gère ni le changement dynamique de direction (IN/OUT décidé par le script à l'exécution), ni la résolution de bus si plusieurs composants pilotent le même fil.
  - Synchro uniquement aux points sleep/réveil, sans tick périodique — écartée : un script en boucle serrée sans `sleep` rendrait ses écritures GPIO invisibles côté Modelica jusqu'à son prochain sleep, ce qui casserait la fidélité de la simulation dans ce cas.
  - Entrée lue comme un simple instantané au moment du sync, sans `when` de transition dédié — écartée : une transition en entrée strictement comprise entre deux syncs (sleep/tick) serait alors invisible pour le script, ce qui est incompatible avec la propriété recherchée (« aucun changement d'état sans que le script soit sollicité ») et gênerait la future implémentation des interruptions (cf. TODO).
  - Historique des fronts accumulés côté Modelica (file consultée par le script à son prochain sync) — écartée pour l'instant : ajoute un état et une API supplémentaires au shim pour un besoin déjà couvert plus simplement par la synchro événementielle par transition.
  - **Connecteurs `Modelica.Electrical.Digital` avec tri-state `Tristates.BUF3S` par broche** — un temps envisagé comme remplacement du connecteur logique simple, avec `WiredX` pour la résolution multi-pilotes. Écarté au profit du domaine `Analog` (électriquement réaliste, résolution multi-pilotes native via les lois de Kirchhoff, pas besoin de `WiredX` en v0 - un seul pilote par fil).
- **Notes pour plus tard** : la période du tick de synchro minimal est un paramètre à calibrer (compromis fidélité / coût de simulation). Si les entrées changent très fréquemment, la synchro par transition peut multiplier les appels à `PyRuntime_sync` — surveiller le coût de simulation dans ce cas. Base naturelle pour les futures interruptions sur changement de pin (cf. TODO).

**Précision (conséquence directe des choix ci-dessus)** : entre deux points de synchro, une broche pilotée par le script (`Pin.OUT`) garde sa dernière valeur (échantillonné-bloqué, pas de variation continue côté sortie). Une broche en lecture (`Pin.IN`) déclenche elle-même un sync dès qu'elle change (cf. ci-dessus) ; en dehors de ces transitions, ce que voit le script reste la dernière valeur connue — le solveur peut évaluer le modèle plusieurs fois entre deux événements (pas variable), ça n'affecte pas ce que voit le script.

### Décision : Domaine électrique vs logique pur pour les broches GPIO

- **Contexte** : en investiguant l'implémentation du connecteur `Modelica.Electrical.Digital` initialement retenu, il s'est avéré que ce domaine est purement logique (énumération 9 niveaux IEEE 1164, pas de tension/courant) — un microcontrôleur ainsi modélisé ne pourrait pas piloter un vrai circuit électrique (LED+résistance, moteur, capteur, diviseur de tension...), alors que c'est explicitement le besoin (systèmes physiques, prototypes, cf. section Besoin). Vérifié : aucun pont Digital↔Analog tout fait n'existe dans la bibliothèque standard installée (`Modelica.Electrical.Digital.Converters` ne fait que Digital↔signal `Real`, pas Digital↔`Modelica.Electrical.Analog.Interfaces.Pin`).
- **Choix retenu** : chaque broche GPIO expose un vrai connecteur électrique `Modelica.Electrical.Analog.Interfaces.PositivePin` (tension/courant réels, lois de Kirchhoff), avec un pont interne par broche composé de blocs standards `Modelica.Electrical.Analog` :
  - `Sources.SignalVoltage` : tension pilotée (`VOH`=3,3 V / `VOL`=0 V) par un signal `Real` calculé à partir de la valeur/direction retournées par `PyRuntime_sync`, quand la broche est en sortie.
  - `Basic.Resistor` (en série) : résistance de sortie approximative (« drive strength »), valeur par défaut 100 Ω.
  - `Ideal.IdealOpeningSwitch` : ouvert (haute impédance) quand la broche est en entrée (`control = not pinIsOutput`), fermé (relie la source au connecteur) quand elle est en sortie — remplace le mécanisme tri-state qu'on cherchait dans le domaine Digital, mais nativement électrique.
  - `Sensors.VoltageSensor` : mesure la tension réellement présente sur le connecteur (indépendamment de l'état de l'interrupteur), comparée aux seuils `VIL`/`VIH` pour reconstituer le booléen `pinBoolIn` transmis à `PyRuntime_sync`.
  - Un seul connecteur par broche suffit (pas de connecteurs `_drv`/`_sns` séparés envisagés un temps pour le domaine Digital) : la résolution multi-pilotes est native en `Analog` (sommation des courants, loi de Kirchhoff), donc pas besoin d'un composant de résolution de bus explicite en v0 (un seul pilote par fil).
- **Alternatives envisagées** :
  - Rester en domaine `Digital` pur (logique uniquement) — écarté : incompatible avec l'intégration à de vrais circuits électriques, qui est le cœur du besoin.
  - Pont électrique avec source idéale (impédance de sortie nulle, pas de résistance série) — plus simple, mais irréaliste face à un vrai circuit chargé (pas de limitation de courant). Gardé en plan de repli si `Resistor`+`IdealOpeningSwitch`+`SignalVoltage`+`VoltageSensor` posait un problème de boucle algébrique (n'a finalement pas été nécessaire, `checkModel` et la simulation passent sans souci avec la résistance série).
- **Notes pour plus tard** : les niveaux de tension (`VOH`/`VOL`/`VIH`/`VIL`) et la résistance série sont des approximations RP2040 raisonnables mais pas des valeurs datasheet exactes (cf. `Interfaces` package) — à affiner si un usage plus poussé le demande. Généraliser à `WiredX`/résolution multi-pilotes explicite si des scénarios multi-instances/multi-pilotes apparaissent au-delà du point-à-point simple de la v0.
- **Piège 3 (bouclage électrique entre deux broches du même `MCU` : tension pilotée disparue des résultats)** : découvert en construisant `Examples.PinEcho` (`GP1` oscille, `GP2` relit électriquement l'état de `GP1` via un câblage dans le schéma, `GP3` reproduit). Deux sous-problèmes distincts, isolés par bissection méthodique (retrait du bouclage, remplacement par différents mécanismes, scripts minimaux à une seule broche, logs `-lv LOG_EVENTS`/`LOG_NLS`, impression de traces Python à chaque étape du script) :
  - **a) Broches GPIO non utilisées totalement flottantes** : `GP0`/`GP4`-`GP7` sans aucun câblage (ni charge, ni résistance de tirage) rendent le système non-linéaire résolu à l'initialisation singulier dès qu'un bouclage électrique relie deux autres broches du même `MCU` (échec de convergence Newton, `LOG_NLS` : « Solving non-linear system ... failed »). Absent dans les scénarios précédents car aucun ne bouclait deux broches entre elles. **Correctif d'origine** : tirer chaque broche inutilisée à la masse par une résistance (1 kΩ), comme déjà fait dans `BasicBlink.mo` — convention appliquée systématiquement à toute broche du pont GPIO non reliée à rien d'autre dans un schéma.
    - **Revu (session suivante)** : demande de simplification de l'utilisateur (« Ça n'a pas de sens » de tirer à la masse une broche non utilisée) — retesté en retirant ces résistances de tirage de tous les exemples, y compris `PinEcho.mo` (le seul avec un vrai bouclage `GP1`↔`GP2`, cas exact qui avait déclenché ce piège à l'origine). **Résultat : `checkModel` et les 9 scénarios `verify_0N` passent tous sans ces résistances**, y compris `verify_06_pin_echo`. La singularité décrite ci-dessus ne se reproduit donc plus dans l'état actuel du modèle (probablement changé par les évolutions ultérieures de `MCU.mo` — ADC/PWM — qui ont modifié le nombre d'équations/variables et donc le point de départ du solveur ; cause exacte non ré-investiguée, non nécessaire puisque le comportement observé est désormais correct). **Convention actuelle** : les broches non utilisées sont laissées non connectées dans tous les exemples ; ce paragraphe reste comme trace de la cause d'origine, à ressortir si la singularité réapparaît un jour (ex. après une future modification substantielle de `MCU.mo`).
  - **b) Bouclage électrique exact entre deux broches du même `MCU` fait disparaître la tension pilotée des résultats** : même une fois (a) corrigé, relier `GP1` à `GP2` par un `connect()` direct — ou tout mécanisme électriquement équivalent testé (résistance quasi nulle, paire capteur de tension + source de tension idéale) — fait que `GP1.v` (et toute variable alias sur le même nœud : `r1.n.v`, `led1.v`...) reste bloquée à ~0 V dans les résultats de simulation, **alors que le script lui-même voit bien les bonnes valeurs en direct** (vérifié en ajoutant des `print()` à chaque étape : `pin2.value()` alterne correctement 1/0 en phase avec `pin1.on()`/`off()`, preuve que le calcul électrique interne est correct pendant l'exécution). La rupture n'apparaît que dans ce qui est écrit/relu dans le fichier de résultats — probablement une conséquence de la fusion d'alias que fait OpenModelica entre `pinNodeVoltage[i]` (broche pilotée) et `pinNodeVoltage[j]` (broche bouclée dessus) quand elles sont algébriquement identiques, qui interagit mal avec le tableau `pinBoolIn` passé à la fonction externe `PyRuntime_sync` et/ou le `when` combinant les 9 broches — cause exacte non identifiée avec certitude au niveau du code généré par `omc`, non reproduite en dehors de ce cas précis. **Correctif** : donner au bouclage un véritable état dynamique plutôt qu'un alias algébrique exact — une résistance de liaison (`loopR`) suivie d'un condensateur à la masse (`loopC`), avec une constante de temps RC choisie négligeable (1 µs, très en dessous de la cadence du scénario) pour ne rien changer au comportement observable, empêche la fusion d'alias et fait réapparaître `GP1.v` correctement dans les résultats. Vérifié par bissection (testé sans bouclage, avec bouclage direct, avec résistance seule, avec capteur+source, puis avec RC) et par script instrumenté de `print()` confirmant que le comportement runtime était correct pendant toute la bissection — seule la version RC est correcte à la fois en direct et dans les résultats stockés.
  - **Notes pour plus tard** : si un futur besoin nécessite de relier deux broches du même `MCU` (ou plus généralement de créer un nœud électrique partagé entre deux sorties du pont GPIO), reproduire le motif `loopR`/`loopC` de `PinEcho.mo` plutôt qu'un `connect()` direct. Signaler ce comportement à la communauté OpenModelica si l'usage s'en présente l'occasion (pas fait à ce stade, cause exacte non confirmée).

### Décision : ADC (entrées analogiques, `machine.ADC`)

- **Contexte** : premier point non coché du TODO, choisi comme chantier suivant après `PinEcho`. Question d'architecture tranchée avec l'utilisateur (`AskUserQuestion`) : les 8 broches `GP0`-`GP7` sont-elles utilisables en double usage (numérique **ou** analogique, au choix du script, comme sur le vrai RP2040) ou via des connecteurs `ADC0`/`ADC1`/`ADC2` dédiés (plus simple, mais moins fidèle) ?
- **Choix retenu** : double usage sur `GP0`-`GP7` (option la plus fidèle au RP2040 réel, retenue par l'utilisateur malgré la recommandation initiale — plus simple — des connecteurs dédiés). Concrètement, le pont GPIO existant calculait déjà une tension continue par broche (`pinNodeVoltage[i] = sns[i].v`, via le `VoltageSensor` déjà présent) — seule sa version seuillée (`pinBoolIn`) traversait la fonction externe `PyRuntime_sync`. L'ADC transmet en plus la version brute : `PyRuntime_sync` gagne un paramètre d'entrée `pinAnalogIn[9]` (aligné sur `pinBoolIn`), rempli côté `MCU.mo` avec `pinNodeVoltage` (déjà calculé par la boucle `for i in 1:9`, resté `protected`). Aucun nouveau connecteur, aucune nouvelle icône, aucun nouveau déclencheur de `when` : l'ADC n'a pas d'IRQ sur le vrai MicroPython non plus, le script l'interroge à la demande (nouvelle primitive native `adc_read`, même point de synchro que `pin_read`). Côté shim, `machine.ADC(id)` (entier ou objet `Pin`) expose `.read_u16()` : lit la tension brute puis la met à l'échelle sur une référence 3,3 V codée en dur dans le shim (`raw = round(v / 3.3 * 65535)`, bornée à [0, 65535]).
- **Alternatives envisagées** :
  - Connecteurs `ADC0`/`ADC1`/`ADC2` dédiés, entrée analogique pure — plus simple à raisonner (aucun risque de retrouver un bug du même genre que le piège 3 ci-dessus, puisqu'aucune broche n'aurait été électriquement partagée entre deux usages), mais moins fidèle au RP2040 réel où une broche GPIO physique sert aux deux usages. Écartée par l'utilisateur.
- **Notes pour plus tard** :
  - La référence de l'ADC (3,3 V) est codée en dur dans le shim Python, pas plombée sur le paramètre `VOH` de `MCU` (qui n'est pas transmis au runtime) — si `VOH` est changé sur une instance, l'échelle de l'ADC ne suit pas. À corriger si ce paramètre devient réellement configurable en pratique (ex. transmettre `VOH` comme argument supplémentaire de `PyRuntime_new`).
  - Contrairement au vrai Pico (seules `GP26`-`GP28` sont ADC-capables), les 8 broches `GP0`-`GP7` le sont toutes ici — simplification v0 assumée (cf. restrictions), cohérente avec le fait que `GP0`-`GP7` ne correspondent déjà pas à la numérotation réelle du Pico.
  - Pas d'échantillonnage périodique ni d'événement de seuil sur l'ADC (contrairement aux broches numériques, dont une vraie transition réveille le script) — la fraîcheur d'une lecture est bornée par le prochain point de synchro (tick périodique par défaut), cohérent avec l'absence d'IRQ sur `machine.ADC` en MicroPython réel.
  - **Vérifié empiriquement que ce changement ne reproduit pas le piège 3 ci-dessus** : `pinAnalogIn`/`pinNodeVoltage` est une grandeur déjà calculée par broche, transmise sous une deuxième forme (brute en plus de seuillée) — aucune nouvelle liaison électrique n'est créée entre deux broches distinctes, à la différence du bouclage `PinEcho`. `checkModel` et `verify_07_adc_read.mos` confirment un comportement correct dès la première implémentation, sans bissection nécessaire cette fois.

### Décision : PWM (sorties modulées, `machine.PWM`)

- **Contexte** : chantier suivant après l'ADC (« tu peux tenter le développement du PWM »). **Décision d'architecture prise seul, sans l'utilisateur** (absent au moment de ce chantier, autorisation donnée en amont) — à challenger à la prochaine relecture si l'approche pose un problème, comme cela a déjà été le cas pour `PinEcho`.
- **Difficulté spécifique** : un PWM réel oscille à des fréquences (souvent 100 Hz-20 kHz+) totalement hors de portée du mécanisme de synchro existant si chaque front devait passer par un aller-retour avec le thread Python (des milliers de synchros par seconde simulée, alors que le mécanisme actuel repose sur un thread OS + section critique, pensé pour des points de synchro peu fréquents).
- **Choix retenu** : le script configure fréquence et rapport cyclique via le shim (`machine.PWM`, points de synchro classiques mais peu fréquents en pratique — typiquement une seule fois), et c'est **Modelica qui génère le créneau réel en continu**, de façon totalement autonome vis-à-vis du thread Python une fois configuré — fidèle au vrai périphérique matériel PWM du RP2040, qui tourne indépendamment du CPU une fois programmé. Concrètement :
  - `PyRuntime_sync` gagne deux tableaux de sortie supplémentaires, `pwmFreq[9]`/`pwmDuty[9]` (Hz / 0-1), remplis par les nouvelles primitives natives `pwm_set_freq`/`pwm_set_duty` (même point de synchro que `pin_write`). `pwmFreq[i] > 0` signale que la broche `i` est en mode PWM plutôt qu'en sortie numérique classique.
  - Côté `MCU.mo`, dans la boucle `for i in 1:9` déjà existante : `pwmPeriod[i] = 1/max(pwmFreq[i], 1e-6)` (plancher pour éviter une division par zéro quand la broche n'est pas en PWM) et `src[i].v` bascule entre le comportement numérique classique (`pinBoolOut[i]` → `VOH`/`VOL`) et un créneau `if mod(time, pwmPeriod[i]) < pwmDuty[i]*pwmPeriod[i] then VOH else VOL` quand `pwmFreq[i] > 0`. Aucun nouveau connecteur, aucune nouvelle icône, aucun nouveau déclencheur de `when` — la génération du créneau est purement continue (événements de croisement de zéro natifs Modelica sur la comparaison `mod(...)`, pas d'appel à la fonction externe).
  - Côté shim, `machine.PWM(pin, freq=None, duty_u16=None)` (accepte un entier ou un objet `Pin`) expose `.freq(f=None)`/`.duty_u16(d=None)` (accesseur si appelé sans argument, mutateur sinon — valeur mise en cache côté Python, pas de nouvel appel natif pour la lecture) et `.deinit()` (repasse la broche en sortie numérique classique, `pwmFreq` remis à 0).
  - Construire un `PWM` prend la broche en sortie (`pin_is_output[idx] = 1`), comme sur le vrai RP2040.
- **Validé empiriquement AVANT d'implémenter dans le vrai modèle** (méthode retenue après l'expérience `PinEcho` : tester le mécanisme le plus incertain en isolation avant de l'intégrer) — modèle Modelica minimal (`discrete Real freq/duty`, `v = if mod(time, période) < duty*période then VOH else 0`) simulé via `omc` : forme d'onde correcte à 200 Hz et 1 kHz (vérifiée point par point), changement de rapport cyclique en cours de simulation correct (à condition d'assigner toutes les variables discrètes concernées depuis un **seul** `when` combiné — deux `when` séparés assignant la même variable rendent le système sur-déterminé, erreur `checkModel` explicite, corrigée avant d'toucher au vrai modèle), performance négligeable (~1000 périodes simulées en une fraction de seconde). Implémenté ensuite dans `MCU.mo`/`PyRuntimeImpl.c` sans bissection nécessaire — `Examples.PwmLed` fonctionne du premier coup (`checkModel` + `verify_08_pwm.mos`, vérifié front par front).
- **Alternatives envisagées** :
  - Piloter chaque front depuis le thread Python (comme les broches numériques classiques) — écartée d'emblée : impraticable aux fréquences PWM réelles (cf. difficulté ci-dessus).
  - `Modelica.Blocks.Sources.Pulse` (bloc standard MSL déjà conçu pour un train d'impulsions période/rapport cyclique/amplitude) — écarté : ses paramètres sont fixés à la traduction (`parameter`), pas modifiables en cours de simulation depuis un signal, alors que le script doit pouvoir changer `freq()`/`duty_u16()` en cours de route.
- **Notes pour plus tard** :
  - Pas de modélisation des « slices » matériels du RP2040 (sur le vrai Pico, deux broches voisines partagent normalement un canal de fréquence commune) — chaque broche a sa fréquence/rapport cyclique indépendants en v0, simplification dans l'esprit du reste du projet (8 broches et non 29, ADC sur les 8 broches et non seulement 3, etc.).
  - `deinit()` repasse la broche en sortie numérique classique pilotée par `pinBoolOut` (bas par défaut, jamais écrit tant que le PWM était actif) plutôt qu'en haute impédance — simplification v0 à documenter si un usage plus poussé le demande.
  - Le créneau est généré par une comparaison continue (`mod(time, période) < ...`), qui génère un événement de croisement de zéro Modelica à chaque front — pas mesuré de ralentissement notable jusqu'à 1 kHz sur quelques secondes simulées lors des tests d'isolation, mais à surveiller si un scénario combine PWM haute fréquence et longue durée simulée (pas encore rencontré en pratique).

### Décision : Interruptions sur broche (`machine.Pin.irq`) et minuteurs logiciels (`machine.Timer`)

- **Contexte** : dernier morceau du chantier « Timers / délais / interruptions » du TODO (`time.sleep` déjà fait). Les deux fonctionnalités se greffent sur le protocole de synchro existant (thread worker ↔ Modelica, `PyRuntimeImpl.c`) **sans aucun changement à `MCU.mo` ni à `Internal/PyRuntime_sync.mo`/`.h`** : Modelica réagit déjà à n'importe quel `nextWakeTime` calculé côté C, et le `when` de `MCU.mo` appelle déjà `PyRuntime_sync` sur toute transition d'une broche en entrée, qu'un callback y soit enregistré ou non. Comportement existant impérativement préservé (scénario 3, `InputReactivity`, déjà validé) : une broche en entrée qui change réveille le worker immédiatement, y compris en plein `sleep()` — ce `sleep()` retourne alors en avance. C'est la « réactivité en entrée », volontaire.
- **Choix retenu (`Pin.irq(handler, trigger)`)** : puisqu'une transition d'entrée réveille déjà le worker, il suffit d'enregistrer un callback à appeler à ce réveil, sans nouvelle boucle de retry. Nouveaux champs par broche dans `PyRuntimeHandle` (`pin_irq_handler`/`pin_irq_self`/`pin_irq_trigger`/`pin_irq_pending`) ; dans la boucle par broche déjà existante de `PyRuntime_sync` (celle qui calcule `input_changed`), sur un vrai flip de valeur d'une broche en entrée avec un handler enregistré dont le `trigger` correspond au sens du front, le callback est marqué « dû ». Nouvelle native `pin_irq_set(id, pin_self, handler_ou_None, trigger)` (point de synchro, comme tout appel mutant du shim). Shim : `Pin.IRQ_RISING = 1`, `Pin.IRQ_FALLING = 2`, `Pin.irq(handler=None, trigger=IRQ_RISING|IRQ_FALLING, **kwargs)` (`**kwargs` absorbe `hard=`/`priority=`/`wake=` de l'API réelle, acceptés mais sans effet — pas de notion de contexte d'interruption matérielle possible dans ce modèle mono-thread).
- **Choix retenu (`machine.Timer`) — la partie délicate** : un timer PÉRIODIQUE doit continuer à se déclencher PENDANT un `sleep()` déjà en cours, sans jamais le faire retourner en avance (contrairement à une vraie transition d'entrée, où le retour anticipé est voulu). Pool fixe `MAX_TIMERS = 4` (même esprit que les 8 broches GPIO plutôt que 29). Mécanisme de « pitstop » : `yield_to_modelica` passe de `void` à `int` (code retour) et gagne une boucle de retry — à chaque réveil du worker, si ni son échéance propre (`wake_at`) n'est atteinte, ni une vraie transition d'entrée n'a eu lieu (`wake_had_input_change`, posé par `PyRuntime_sync` avant de réveiller le worker), alors ce n'est qu'un « pitstop » : les callbacks dus (IRQ + Timer, dispatch unique via `run_due_callbacks`) sont exécutés puis le MÊME `wake_at` est reposté, sans laisser l'appel bloquant en cours (`native_sleep`, etc.) reprendre la main trop tôt. La boucle `for(;;)` déjà existante de `PyRuntime_sync` (celle qui draine les réveils immédiats chaînés, cf. piège ci-dessous) n'a besoin d'aucun changement structurel pour composer avec ça — elle tolère déjà plusieurs allers-retours au même `currentTime`, exactement le motif d'un pitstop. Deux ajouts dans son corps : un terme `OR` supplémentaire dans la condition de réveil (« un timer actif est dû ») et `*nextWakeTime = min(réveil propre du worker, prochaine échéance active)`, recalculé après tout réarmement survenu pendant l'appel.
- **Point de verrouillage critique** : `run_due_callbacks` rassemble les callbacks dus **sous verrou** (`Py_XINCREF` sur les références récupérées), **relâche complètement `cs`**, puis seulement alors appelle `PyObject_CallFunctionObjArgs`. Appeler du Python en tenant encore `cs` provoquerait un deadlock réel : `SleepConditionVariableCS` ne relâche qu'**un seul niveau** de section critique, alors qu'un callback qui touche une broche (`pin.value(...)`) ré-entre `EnterCriticalSection` avant de rappeler `yield_to_modelica`, laissant `cs` techniquement encore tenu quand Modelica devrait pouvoir le reprendre. Un callback qui pilote une broche ou dort est le cas d'usage *normal*, pas un cas limite.
- **Propagation d'erreur si un callback lève** : ne pas appeler `PyErr_Print()`/avaler l'exception dans `run_due_callbacks` — laisser `PyErr` positionné et remonter un code d'erreur (`yield_to_modelica` retourne `-1`). Chaque site d'appel natif existant (`native_pin_init`, `native_pin_write`, `native_pin_read`, `native_adc_read`, `native_pwm_set_freq`, `native_pwm_set_duty`, `native_pwm_deinit`, `native_sleep`) gagne une garde `if (yield_to_modelica(...) != 0) return NULL;`. Mécanisme standard CPython (retourner `NULL` avec une exception positionnée), qui remonte naturellement jusqu'à `PyRun_SimpleString` — déjà câblé sur `ModelicaFormatError` via le relais stdout/stderr existant. Donc une exception dans un callback IRQ/Timer est traitée exactement comme une exception non gérée au niveau du script principal, sans nouveau code de rapport d'erreur.
- **Piège découvert en session (tempête d'événements à durée simulée nulle)** : un `Timer(period=0)` (ou période sous l'epsilon de tolérance) redeviendrait dû immédiatement après son propre déclenchement — contrairement au bug historique des réveils immédiats chaînés (borné, drainé en une seule boucle C interne), celui-ci provoquerait une **suite non bornée d'événements Modelica à durée simulée nulle** (chaque pitstop retourne à Modelica puisque le `sleep()` du worker est lointain — la boucle de drain de `PyRuntime_sync` ne le contient pas, elle ne s'applique qu'au sein d'un même `currentTime`). **Correctif** : `native_timer_init` rejette (`ValueError`) toute période sous un plancher `TIMER_MIN_PERIOD = 1 ms` (cohérent avec la granularité réelle de `machine.Timer` sur RP2040, même style que `native_pwm_set_freq` qui rejette déjà les fréquences négatives).
- **Validé par test isolé avant intégration** (méthode déjà établie pour `PinEcho`/PWM), puis sur le vrai modèle électrique (`Examples.PinIrq`, `Examples.TimerToggle`, `verify_10_pin_irq.mos`, `verify_11_timer.mos`) : `PASS` dès la première intégration. Détail du harnais de pré-check : cf. `requirements-archive.md`.
- **Alternatives envisagées** :
  - Vraie boucle d'interruption matérielle (contexte séparé, préemption du script principal) — hors de portée : ce modèle n'a qu'un seul thread worker, exécuté en ping-pong strict avec Modelica ; aucune notion de préemption n'existe.
  - Isoler une exception de callback (logguer et continuer plutôt qu'arrêter toute la simulation) — écarté pour la v0 : demanderait un mécanisme de rapport d'erreur séparé, alors que réutiliser le chemin d'erreur du script principal est gratuit et cohérent avec la décision « Comportement en cas d'exception ».
- **Notes pour plus tard** :
  - `MAX_TIMERS = 4` et `TIMER_MIN_PERIOD = 1 ms` sont des choix v0 assumés, à agrandir/ajuster si un usage réel le demande.
  - Références `PyObject*` accumulées par les callbacks IRQ/Timer (comme le reste de l'état Python du runtime) jamais explicitement décrémentées à `PyRuntime_destroy` — cohérent avec le choix déjà documenté (processus recréé à chaque run, cf. décision « Mécanisme d'exécution »).
  - Piste évoquée (pas retenue pour l'instant) : exécuter les callbacks dans un thread dédié plutôt que sur le thread worker existant, pour une sémantique plus proche d'une vraie interruption matérielle — cf. TODO dédié dans « TODO vers une version exhaustive », à peser contre la complexité de concurrence que ça introduirait.

### Décision : Périphérique d'affichage pédagogique (`Peripherals.Display`) — remplace le chantier initial « Bus UART/I2C »

- **Contexte initial** : ce périphérique remplace un chantier plus large (« Bus UART/I2C ») qui avait démarré avec deux périphériques dédiés et un vrai port UART bidirectionnel sur `MCU` — historique complet dans `requirements-archive.md`.
- **Revu à la demande de l'utilisateur (simplification du périmètre)** : ce périmètre a été jugé trop ambitieux pour gérer plusieurs périphériques dans une v0 pédagogique. Décision explicite de ne garder qu'**un seul périphérique pédagogique d'affichage**, et de retirer toute terminologie de protocole réel (« UART », « Serial », « LCD ») pour éviter toute ambiguïté avec un vrai bus de communication — le composant s'appelle simplement `Peripherals.Display`, la liaison `Interfaces.DisplayLinkOutput`/`DisplayLinkInput`, le port sur `MCU` `Display0`. **Retiré** : `UART0Rx` (le port MCU redevient un port de sortie unique, `Display0`), `Peripherals.TemperatureSensor` et son exemple, la notion de bus adressable/I2C. L'API script devient `machine.Display(0).write(texte)` (plus de `machine.UART`, plus de `.any()`/`.readline()` — écriture seule, composant pédagogique et non un vrai protocole). Le port `Display0` est positionné sur le bord supérieur de l'icône `MCU`, aligné avec `GP4` (à droite), plutôt qu'au centre comme l'ancien `UART0Tx`/`UART0Rx`.
- **Choix retenu (connecteur)** : liaison modélisée par des connecteurs Modelica **causaux** (façon `Modelica.Blocks.Interfaces.RealOutput`/`RealInput` : deux classes de causalité opposée plutôt qu'un connecteur bidirectionnel), portant directement le message logique (texte) au lieu d'une tension/d'un courant — **pas** `Modelica.Electrical.Analog` comme pour les GPIO. Livraison instantanée au point de synchro suivant, pas de bauds ni de forme d'onde série simulés. Justification de la divergence par rapport au principe électrique des GPIO (cf. décision « Domaine électrique vs logique pur ») : ce principe existe parce que le besoin central du projet est de piloter de vrais circuits (LED+résistance, moteur, capteur...) ; ce périphérique n'est pas de l'électronique passive ayant besoin d'un vrai courant pour fonctionner, c'est un composant réagissant à un message logique — la fidélité électrique n'apporte rien ici et coûterait cher (même difficulté que celle déjà rencontrée, et résolue différemment, pour le PWM). Connecteurs : `Interfaces.DisplayLinkOutput` (sur `MCU`, sortie) / `DisplayLinkInput` (sur `Peripherals.Display`, entrée) — `seq: Integer` + `payload: String` + `charCode[DISPLAY_COLS]: Integer` (`seq` sert de déclencheur d'edge-detection `change(seq)`, plus fiable qu'une comparaison de `String`).
- **Nouveaux champs `PyRuntimeHandle` (`PyRuntimeImpl.c`)** : `display_seq: int`, `display_payload[DISPLAY_MSG_MAX_LEN+1]: char` (`DISPLAY_MSG_MAX_LEN = 128`, tronque au-delà — restriction v0 assumée), scalaires (pas de tableau, un seul port possible). Nouvelle native `display_write(id, text)` : tronque dans le buffer, incrémente `seq`, puis `yield_to_modelica(sim_time)` — réutilise tel quel le point de synchro immédiat déjà utilisé par `pin_write`. `PyRuntime_sync` gagne deux sorties scalaires (`displaySeqOut: int*`, `displayPayloadOut: const char**`, via `ModelicaAllocateString`), assignées directement aux champs du connecteur dans le tuple du `when` existant — pas de variable `protected` intermédiaire nécessaire (un champ `output` de connecteur est une variable assignable ordinaire). Shim : `class Display` avec `__init__(id=0, **kwargs)` (signature volontairement minimale, composant pédagogique et non un vrai protocole) et `.write(text)` (accepte `str` ou tout objet convertible via `str()`).
- **Livraison instantanée, message entier d'un coup** : pas de simulation octet-par-octet ni de débit en bauds réel — simplification v0 délibérée (mirrors le choix déjà fait pour l'ADC/PWM de ne pas simuler chaque front individuellement quand ça n'apporte rien à l'usage pédagogique visé).
- **Piège (String non stockée dans les résultats de simulation)** : une `String` n'est écrite dans **aucun** format de résultat de simulation (`.mat`/`.csv`, vérifié empiriquement via un pré-check isolé, `Sandbox/StringProbe.mo`) — limitation fondamentale du format de trajectoire Modelica (numérique uniquement), pas un bug de `DynamicSelect` lui-même. Contournée sans jamais stocker de `String` : cf. le choix retenu « Affichage réel du texte » plus bas. Détail du pré-check : `requirements-archive.md`.
- **Leçon générale (connecteur causal `input` optionnel)** : ne jamais donner de valeur par défaut inconditionnelle sur les champs d'un connecteur causal `input` — ça entre en conflit avec l'équation générée par `connect()` dès qu'un modèle le connecte réellement (`Error: Too many equations, over-determined system` dans cette installation `omc`). Passer par un garde `cardinality()` côté modèle propriétaire à la place. Rencontré à l'époque de l'ancien port `UART0Rx` (retiré depuis) — récit complet dans `requirements-archive.md`.
- **Choix retenu (affichage réel du texte sur l'icône)** : demande explicite de l'utilisateur (« l'écran LCD affiche réellement... d'un point de vue pédagogique, ça aiderait »), après un premier tour où l'icône réactive par couleur seule avait été retenue. Plutôt qu'un rendu pixel par pixel (police en matrice de points, ~20×35 formes par ligne de caractères — jugé disproportionné, cf. ancienne alternative ci-dessous) : nouvelle fonction utilitaire partagée `Internal.StringToCharCodes(s, n)` (`external "C"`, `Resources/Include/StringToCharCodes.c`, indépendante de `PyRuntime` — juste `strlen`/indexation de caractères, aucune dépendance Python), qui convertit les `n` premiers caractères d'une `String` en un tableau `Integer[n]` de codes ASCII (complété par des espaces si plus court). Un `Integer`, contrairement à une `String`, **est** stocké dans les résultats de simulation (déjà vérifié via `mcu.Display0.seq`) — donc `DynamicSelect(..., textString)` peut s'animer correctement s'il est piloté par une expression `if/elseif` sur un `charCode[i]` stocké plutôt que directement sur une `String`. Constante `Interfaces.DISPLAY_COLS = 20` (fidèle à un vrai afficheur 20 colonnes — au-delà, un message est tronqué sur l'icône uniquement, le texte complet reste disponible intégralement dans le journal). `DisplayLinkOutput`/`DisplayLinkInput` portent un champ `charCode[DISPLAY_COLS]` ; `MCU.mo` le calcule dans le même `when` que `Display0.payload` (`Display0.charCode = Internal.StringToCharCodes(Display0.payload, Interfaces.DISPLAY_COLS)`). `Peripherals.Display.mo` : 40 éléments `Text` (20 colonnes × 2 lignes), chacun `DynamicSelect(" ", if abs(code - 65) < 0.5 then "A" elseif ... else " ")` — jeu de caractères supporté : espace, chiffres, lettres majuscules/minuscules, ponctuation courante (`! ' , - . ?`, ~69 caractères), un caractère hors de cet ensemble s'affiche comme un espace. Fichier `.mo` généré mécaniquement (script Python jetable produisant le bloc `if/elseif` répété par colonne, écrivant directement le fichier final plutôt qu'être recopié à la main) pour éviter les erreurs de transcription sur ~70 branches × 40 colonnes.
  - **Défilement 20×2 réel, écran fixe** : (1) **Écran fixe** : pas de variation lumineuse (l'ancien mécanisme `glow`/`lastRxTime`/`screenOn`/`screenOff` — `DynamicSelect(fillColor, ...)` interpolé, décroissance exponentielle après réception — entièrement retiré) ; l'écran affiche une couleur vert clair constante (`{190, 255, 190}`), le texte lui-même suffisant à indiquer l'activité. (2) **Vrai défilement à deux lignes** (comme un afficheur physique) : variable publique `discrete Integer line2CharCode[DISPLAY_COLS]` dans `Display.mo`, mise à jour dans le même `when change(displayLink.seq) then ... end when` que le `print()` : `line2CharCode = pre(displayLink.charCode)` — capture l'état de la ligne 1 **juste avant** la mise à jour (donc l'ancien message), qui devient la ligne 2 ; la ligne 1 affiche directement `displayLink.charCode` (le message courant, déjà à jour à ce même instant via `connect()`). `pre()` est le seul ajout requis — motif Modelica déjà éprouvé dans le projet (`pre(nextWakeTime)` dans `MCU.mo`).
  - **Validé numériquement** (pas seulement visuellement) : `verify_12_display.mos` vérifie `display.displayLink.charCode[1:3] == {66, 111, 110}` (« Bon » du premier message « Bonjour ») **et** le défilement après le second message (« Ca marche ») : `display.displayLink.charCode[1] == 67` (« C », nouvelle ligne 1) et `display.line2CharCode[1] == 66` (« B », l'ancien message « Bonjour » décalé en ligne 2) — confirme numériquement que le défilement fonctionne, pas seulement que la donnée atteint l'icône. Le rendu **animé** dans OMEdit (scrubbing d'un résultat enregistré) n'a pas pu être vérifié visuellement par l'agent (MCP-OpenModelica ne fournit qu'un rendu statique de l'icône) — mais le mécanisme sous-jacent (`DynamicSelect` sur une expression combinant une grandeur stockée) est déjà celui, identique dans son principe, utilisé et confirmé visuellement pour `Peripherals.LED`/`builtinLed` (interpolation RGB).
  - **Piège évité en amont** : un pré-check `Sandbox/GlyphProbe.mo` a confirmé avant intégration que `if/elseif` retournant des littéraux `String` est accepté dans un `DynamicSelect` — détail dans `requirements-archive.md`.
  - **Piège « grésillement » de l'affichage, corrigé** : l'utilisateur a signalé un scintillement continu du texte en relecture d'un résultat enregistré (pas en direct). Cause : le `.mat` stocke tout en double précision, y compris les `Integer` — la reconstruction par interpolation peut réintroduire un bruit de l'ordre de 1e-6 à 1e-9 autour de l'entier « vrai », faisant échouer une égalité exacte (`charCode[i] == 66`) par intermittence. **Corrigé** par comparaison à tolérance (`abs(charCode[i] - code) < 0.5`, sûre car les codes ASCII sont espacés d'au moins 1) — c'est la comparaison utilisée aujourd'hui dans `Peripherals.Display.mo`. Récit complet : `requirements-archive.md`.
- **Alternatives envisagées** :
  - Rendu de texte littéral sur l'icône via une police en matrice de points (pixel par pixel, ~12×7×5 formes) — écarté au profit du rendu caractère entier par colonne ci-dessus : bien plus lourd (des centaines de formes supplémentaires par colonne au lieu d'un seul `Text`), pour un gain de fidélité non nécessaire (un afficheur caractère, pas un afficheur graphique, est ce qui est modélisé).
  - **Alternative électrique réelle, écartée (tranchée via `AskUserQuestion` lors du chantier initial)** : modéliser la liaison de façon réellement électrique, dans l'esprit de la fidélité déjà appliquée aux GPIO (vrais niveaux de tension, forme d'onde série bit à bit). Non retenu : complexité largement supérieure au bénéfice pédagogique immédiat, hors de portée du mécanisme de synchro par thread actuel (même difficulté que celle déjà rencontrée, et résolue différemment, pour le PWM). Gardé en mémoire comme piste sérieuse pour une version qui viserait un réalisme électrique complet des bus de communication.
- **Notes pour plus tard** :
  - **Idée exprimée par l'utilisateur pour la suite** : tenter une vraie implémentation `machine.UART` sur les broches GPIO (en plus, pas à la place, du `Display` pédagogique ci-dessus) — reste à cadrer (émission/réception, fidélité électrique ou connecteur logique causal comme ici) le moment venu.
  - **Piste v2 (pas retenue) : « intelligence des périphériques ».** Plutôt qu'un composant Modelica à comportement fixe (`Display`), une future version pourrait le rendre programmable en Python : son propre `PyRuntime` (External Object CPython dédié) et son propre script, de sorte que sa réaction à un message reçu soit elle-même scriptable plutôt que câblée en dur dans des équations Modelica. **Mise à jour (chantier « Périphériques UART externes ») : cette note situait mal le verrou.** Rendre un périphérique programmable ne demande **pas** un second interpréteur, donc ne heurte pas la décision « Multi-instances ». Un périphérique n'a pas besoin de se suspendre au milieu de sa pile d'appels — il réagit, il ne dort pas : ses gestionnaires (`on_receive`, `on_tick`) vont au bout et peuvent donc s'exécuter dans le même interpréteur, sans thread ni handshake, chacun dans son propre dictionnaire de globales. Le vrai verrou, vérifié dans le code, est beaucoup plus petit : le thread worker conserve le GIL pendant qu'il est garé. Ce qui reste une v2 du système, c'est un second **microcontrôleur** complet — parce que son script, lui, doit pouvoir `sleep()`, ce qui exige une pile propre, donc un thread, donc de décentraliser `g_current` et de revoir le jeton de synchro à deux places. La frontière n'est pas « périphérique contre microcontrôleur » mais « va-au-bout contre suspendable ».
  - `Bus I2C`/`Bus SPI` du TODO : non commencés, restent des chantiers ouverts et distincts de ce périphérique pédagogique.

### Décision : UART électrique réel sur les broches GPIO (`machine.UART`)

- **Contexte** : chantier ouvert par la note « idée exprimée par l'utilisateur pour la suite » de la décision « Périphérique d'affichage pédagogique » — tenter un vrai `machine.UART` **sur les broches GPIO**, en plus (pas à la place) du `Display` pédagogique. Contrairement au `Display` (liaison logique causale, message livré d'un bloc), l'UART doit être **électriquement réel** : c'est tout son intérêt, un élève doit pouvoir sonder la ligne dans OMEdit et y lire une vraie trame, et à terme y brancher un vrai périphérique série. Périmètre tranché avec l'utilisateur via `AskUserQuestion` (broches configurables, trame 8N1, API `write`/`any`/`read`/`readline`, 1200 bauds par défaut, `write()` non bloquant avec file).
- **Difficulté spécifique** : la même que pour le PWM, en pire. Un UART doit produire des fronts à la cadence des bits (833 µs à 1200 bauds), totalement hors de portée du mécanisme de synchro si chaque front passait par un aller-retour avec le thread Python — et contrairement au PWM (un motif fixe répété indéfiniment), une trame UART encode **une suite d'octets arbitraire poussée à la volée par le script**, apériodique et à état.
- **Choix retenu — partage asymétrique du travail entre Modelica et C**, ce qui est ce qui rend le chantier abordable :
  - **Émission : équation continue Modelica** (transposition du motif PWM). Le C sérialise l'octet en motif de bits complet (`uart_tx_bits[UART_MAX_FRAME_BITS]`, start + data LSB first + stop) et publie ce motif, l'instant du front de start, la durée de bit et le nombre de bits utiles. Modelica calcule `uartTxPhase[i] = (time - uartTxStart)/uartBitDur`, `uartTxBitIdx[i] = floor(...)`, sélectionne le bit courant par un `if/elseif` explicite et pilote `src[i].v` — sans aucun appel à la fonction externe par front, comme le vrai périphérique UART du RP2040 qui tourne indépendamment du CPU une fois programmé.
  - **Réception : machine à états entièrement en C**, dans `PyRuntime_sync`. Au front descendant du start bit (qui déclenche déjà le `when` existant, la broche étant en entrée), le C programme `uart_rx_next_sample = now + 1.5×bitDur` (milieu du premier bit de données) puis un réveil par bit, remontés via `earliest_uart_deadline` → `nextWakeTime` — exactement le mécanisme déjà utilisé par `machine.Timer`. **Aucune nouvelle équation ni aucun nouveau `when` côté Modelica pour la réception** : seule l'émission touche `MCU.mo`.
  - **Le format de trame vit entièrement côté C** (une seule fonction, `uart_tx_begin_frame`) : passer au format paramétrable (parité, 7/9 bits, 2 stop) plus tard ne demandera de toucher ni Modelica ni le shim Python. `UART_MAX_FRAME_BITS = 13` est déjà dimensionné pour ça.
  - Files d'émission et de réception à taille fixe (`UART_TX_BUF_LEN`/`UART_RX_BUF_LEN` = 256 octets) dans le handle — **les premiers FIFO du projet**, le style maison (tableau fixe, pas de `malloc`, rien à libérer puisque `PyRuntime_destroy` est un no-op assumé) restant respecté. `write()` est non bloquant : les octets s'accumulent et les trames s'enchaînent sans trou, la suivante démarrant pile à la fin de la précédente.
- **Point dur identifié à la conception, et corrigé : la réactivité en entrée devait être désactivée sur la broche RX.** `PyRuntime_sync` pose `input_changed = 1` sur tout front d'une broche en entrée, ce qui rend le réveil « authentique » dans `yield_to_modelica` et **fait retourner en avance le `sleep()` en cours** — comportement voulu pour un bouton (scénario « réactivité en entrée »), mais faux pour une broche affectée au périphérique série : à 1200 bauds, chaque octet reçu aurait cassé une dizaine de `sleep()`. **Correctif** : `uart_rx_claimed[]` marque la broche RX, qui est alors exclue du calcul d'`input_changed` — et donc aussi de l'armement des IRQ GPIO, qui vit dans le même `if`. Fidèle au matériel réel, où une broche prise par le périphérique UART ne génère plus d'interruption GPIO. `PyRuntime_sync` reste appelé à ces instants (la condition du `when` est côté Modelica et ignore cette réservation), donc le décodage se fait — mais le worker n'est plus réveillé pour rien.
- **État de repos : c'est le TX qui tient la ligne, et aucune résistance de tirage n'est nécessaire.** Question posée par l'utilisateur (« faut-il prévoir un pull-up, ou juste tenir la ligne à 1 ? »). La sortie TX d'un UART est **push-pull** : elle pilote activement les deux niveaux — bas pour le bit de start et les bits de données à 0, **haut en permanence le reste du temps** (bit de stop, puis état de repos dit « mark »). Le RX, lui, est une simple entrée haute impédance qui n'impose jamais rien. Contrairement à un bus I²C en drain ouvert, un pull-up n'a donc aucun rôle ici ; quand on en met un sur une liaison série réelle, c'est côté **RX** et uniquement pour qu'une entrée débranchée ne flotte pas et ne prenne pas du bruit pour un bit de start — cas sans objet dans un bouclage où TX et RX sont toujours reliés. Concrètement dans le modèle : une broche affectée en TX **reste** pilotée par la branche UART même hors trame (`uartTxPin == i` sans condition sur `uartTxActive`), la branche « hors trame » de `uartTxLevel` donnant le niveau HAUT. Sans ça on retomberait sur `pinBoolOut` (bas par défaut) et le récepteur verrait un bit de start permanent. `Examples.Uart.Loopback` **montre** cet état de repos : le script attend `REPOS_MS = 5` ms avant d'émettre, pour qu'on voie la ligne haute sur l'oscillogramme avant le premier front descendant, et `verify_13` le vérifie numériquement avant et après les trames.
- **Deux détails de correction indispensables trouvés à l'implémentation** :
  - Le décodeur RX doit attendre le **bit de stop** avant de repasser au repos, et non s'arrêter au 8ᵉ bit de données : sinon un dernier bit de données à 0 (ligne basse) serait aussitôt relu comme un nouveau bit de start. Une trame dont le stop n'est pas haut est ignorée (pas de remontée d'erreur de framing en v0).
  - **Le bit de start se détecte sur un FRONT descendant, jamais sur un niveau bas** (`uart_rx_last_level` dans le handle). Bug réel, masqué jusqu'à ce que l'utilisateur demande à voir l'état de repos : au tout premier point de synchro, `PyRuntime_sync` reçoit l'état électrique d'**avant** que le script n'ait configuré l'UART — la broche TX n'est pas encore pilotée et la ligne est à 0 V. Un test sur le niveau y voyait un bit de start et fabriquait un octet fantôme, qui polluait la file de réception. Le défaut était invisible tant que le script émettait dès `t=0` (le faux start coïncidait alors avec le vrai) ; il est apparu dès qu'un délai a été introduit avant le premier `write()`. Exiger le front impose d'avoir vu la ligne au repos au moins une fois avant d'écouter — ce que fait aussi un vrai récepteur UART.
- **Validé en pré-check isolé AVANT de toucher `MCU.mo`** (méthode déjà établie pour PWM/IRQ) — modèle jetable `Sandbox/UartWaveProbe.mo`, sans Python ni `MCU`, des `discrete` posées à la main tenant lieu de sorties du C. Trois points vérifiés : forme d'onde conforme pour deux octets connus, enchaînement de deux trames sans glitch, et surtout **absence d'événements parasites au repos** — 10 s de temps simulé (dont 99,8 % au repos) en 0,31 s, confirmant que l'astuce de la phase constante à `-1.0` hors trame (transposition du plancher `max(pwmFreq, 1e-6)` du PWM) empêche bien `floor()` de croiser quoi que ce soit. Le pré-check a aussi attrapé une erreur avant intégration (variables discrètes sans équation). Modèle supprimé une fois validé.
- **Alternatives envisagées** :
  - **Liaison logique causale avec durée de transmission calculée** (à la `Display`, mais en retardant la livraison de `nbBits/baudrate` au lieu de la livrer instantanément) — quasi gratuite à implémenter puisqu'elle réutilisait tel quel le motif `Display0`, et elle aurait donné une fidélité *temporelle* correcte (le débit influence vraiment le rythme). **Écartée** : elle contredit l'objectif même du chantier — un connecteur logique n'est pas électrique, un oscilloscope branché sur la broche ne montrerait rien, et ça n'aurait été qu'un second `Display` déguisé plutôt qu'un UART.
  - Piloter chaque front depuis le thread Python (motif `PinEcho`) — écartée d'emblée, impraticable aux cadences série réelles.
  - Décoder la réception par une machine à états **en Modelica** (compteur de bits, échantillonnage par `when`) — écartée au profit du décodage en C : Modelica est un langage peu commode pour des compteurs de bits conditionnels, et surtout le mécanisme de réveil programmé (`nextWakeTime`) existait déjà et fait le travail sans une ligne d'équation supplémentaire.
- **Notes pour plus tard** :
  - Format de trame paramétrable (`bits`/`parity`/`stop` réellement implémentés) : accepté en paramètre mais sans effet en v0. Le coût est concentré sur le décodeur RX ; l'émission est déjà prête (le format vit dans `uart_tx_begin_frame`). Intérêt pédagogique réel : montrer qu'un désaccord de configuration entre émetteur et récepteur produit des octets faux, l'erreur n°1 en TP série.
  - `UART_MAX_BAUD = 115200` est un garde-fou contre la tempête d'événements (un événement Modelica par front de bit), même esprit que `TIMER_MIN_PERIOD`. À 115200 bauds sur une longue simulation, le coût reste à surveiller.
  - Un seul périphérique (`UART(0)`), pas de `uart.irq()`, pas de contrôle de flux RTS/CTS, débordement de file silencieux (octets perdus, comme un FIFO matériel qui déborde), erreur de framing silencieuse.
  - La réception ne réveille pas le script : il récupère les octets à son rythme par `any()`/`read()`. Un `uart.irq()` (réception pilotée par interruption) reste possible plus tard en réutilisant le mécanisme de `Pin.irq`.
  - **Multi-instances** : faire dialoguer deux `MCU` distincts par cette liaison se heurte directement à la restriction « une seule instance / un seul interpréteur CPython » (cf. décision « Multi-instances »). Le bouclage sur un seul `MCU` retenu ici valide tout le mécanisme sans y toucher.

### Décision : Périphériques UART externes connectables (`Internal.PartialUartDevice` et ses dérivés)

- **Contexte** : chantier ouvert par l'entrée TODO « nouveau périphérique branché sur l'UART électrique réel ». La décision « UART électrique réel » avait donné une vraie liaison série, mais son seul démonstrateur (`Examples.Uart.Loopback`) bouclait le `MCU` sur lui-même à travers un réseau R+C qui n'existait que pour contourner une fusion d'alias entre deux broches du même composant. Il manquait donc un **interlocuteur** : impossible de monter un TP où le script dialogue avec un capteur. Périmètre tranché avec l'utilisateur via `AskUserQuestion` (un seul composant portant les deux modes, reconnaissance par délimiteur, TX et RX toujours présents, deux ports réels d'échange avec le modèle, sélecteur explicite table/script, quatre appareils dérivés).
- **Choix retenu** : une classe de base `Internal.PartialUartDevice` (`partial`, donc non instanciable), dont on dérive des appareils concrets **par la seule redéfinition de paramètres**. `Peripherals` n'expose que des composants posables dans un schéma : les quatre appareils dérivés, plus `UartGenericDevice` — un appareil entièrement décrit par ses paramètres, pour les cas qui ne justifient pas d'écrire une classe.
  - **Le moteur bit/octet est partagé, pas dupliqué.** Le travail de `pyruntime_uart.c` (files circulaires, sérialisation 8N1, décodage par échantillonnage au milieu de chaque bit, calcul d'échéance) était déjà sans Python ni thread : il a été extrait tel quel dans `Resources/Include/uartcore.h` + `uartcore.c`, à la racine d'`Include/`, et sert désormais aux deux côtés de la liaison. `PyRuntimeHandle` embarque un `struct UartEngine`, et `pyruntime_uart.c` se réduit au choix des broches, aux primitives natives et à la publication. Seul changement de signature : `uartcore_rx_step` reçoit le niveau logique plutôt qu'un tableau de broches.
  - **Un seul mécanisme d'émission, trois sources d'échéances.** Les deux modes alimentent la **même** file d'émission ; seule diffère l'origine des octets. Aux deux échéances déjà présentes (fin de trame, prochain échantillon de réception) s'ajoutent l'échéance de réponse armée et l'échéance périodique, toutes réduites par un `min()` publié en `nextWakeTime`. Les deux modes cohabitent donc sans effort sur une même instance.
  - **Reconnaissance par délimiteur.** `terminator` est un paramètre **chaîne** (un saut de ligne par défaut, seul son premier caractère est retenu) plutôt qu'un code numérique, pour rester lisible dans le dialogue de paramètres. Les octets reçus s'accumulent jusqu'à `terminator` (`\n` par défaut), puis la ligne complète est confrontée à une table compacte `"CMD=>REPONSE|CMD=>REPONSE"`. Une commande fragmentée sur plusieurs trames est donc reconnue sans effort, puisque c'est l'accumulateur qui la réassemble.
  - **Deux ports réels, dans les deux sens.** `{vN}` (avec précision facultative, `{v1:.1f}`) insère `valueIn[N]` dans une trame émise ; `{oN}`, placé dans une *commande*, capture un nombre de la trame reçue vers `valueOut[N]`. Un même composant est donc capteur **et** actionneur, ce qui permet une régulation en boucle fermée entièrement dans le modèle.
  - **Sélecteur explicite plutôt que règle de précédence.** Une `enumeration Interfaces.UartBehaviour` (`Table` / `Script`), rendue en liste déroulante par OMEdit, avec des `Dialog(enable = ...)` qui grisent le groupe hors sujet — l'ambiguïté « les deux sont remplis » ne peut pas se produire. Les champs propres à la table (`commandTable`, `periodicTemplate`, `echoEnabled`…) sont grisés en mode `Script` ; la temporisation (`period`, `responseDelay`) reste active dans les deux modes.
  - **Pont électrique plus simple que celui du MCU** : les directions sont fixes, donc **aucun `IdealOpeningSwitch`** (cf. piège des composants `Ideal.*` commutants plus bas). TX est une `SignalVoltage` + résistance série ; RX est un `VoltageSensor` avec un tirage `RPullUp` vers `VOH`.
- **Point dur trouvé à l'implémentation, et corrigé** : câbler les **deux** sens entre un `MCU` et un périphérique faisait **mourir `omc` silencieusement** (build échoué, `getErrorString()` vide, tous les temps à zéro, aucun fichier généré — alors que `checkModel` passait). Bissection : chaque sens **isolément** compile, seule leur combinaison échoue. Cause : les deux `when` deviennent mutuellement dépendants à travers le réseau électrique (le `change(rxBoolIn)` du périphérique dépend de la tension pilotée par le MCU, et le `change(pinBoolIn[k])` du MCU dépend de celle pilotée par le périphérique). Correction retenue : une **capacité d'entrée `CIn` sur la broche RX du périphérique** (1 nF par défaut). Physiquement honnête — toute broche d'entrée et tout câble en ont une — et elle donne au nœud un véritable état dynamique, ce qui coupe le cycle. Face aux 100 Ω de sortie, la constante de temps vaut 0,1 µs, soit 0,01 % d'un bit à 1200 bauds. **Bénéfice inattendu** : elle rend inutile le réseau R+C artificiel de `PinEcho`/`Uart.Loopback` pour tout montage impliquant un périphérique, puisque chaque extrémité réceptrice porte désormais sa propre capacité.
- **Piège de l'octet fantôme, reproduit à l'envers** : le constructeur initialisait `rx_last_level = 1` au motif que « la ligne est au repos haut ». Elle ne l'est pas à `t = 0` : tant que le script n'a pas configuré son UART, la broche du MCU est une entrée, et le tirage `RPullUp` se retrouve en diviseur avec la fuite de l'interrupteur ouvert du pont GPIO — le nœud est à ~0,3 V, donc **bas**. Vu depuis un état initial à 1, cela ressemble à un front descendant : le décodeur fabriquait un octet fantôme dès le premier point de synchro et restait désynchronisé pour toute la suite (`b'Hi\n'` revenait en `b'*K\xf8'`). `rx_last_level` doit rester à 0, ce qui oblige le décodeur à voir d'abord la ligne monter au repos — exactement le correctif déjà appliqué côté microcontrôleur.
- **Garantie « une fois par événement », exigée explicitement.** Modelica rappelle une fonction externe plusieurs fois au même instant simulé (2 à 3 itérations d'événement, cf. la boucle de drain). Le moteur appelle donc `uartdev_on_line` **une fois par ligne complète** (la ligne est retirée de l'accumulateur dans le même geste) et `uartdev_on_tick` **une fois par échéance franchie**. Le code UART existant y échappait déjà, mais *implicitement*, parce qu'il est piloté par échéances (`while (now >= echeance)`) ; ici c'est une exigence contractuelle, sans quoi la machine d'état de la phase 2 rejouerait ses transitions deux ou trois fois par événement.
- **Deux factorisations au passage** :
  - `Interfaces.uartBitLevel` remplace la chaîne de 13 `elseif` de `MCU.mo` : dans une **fonction** (section `algorithm`), l'indexation par variable est licite, contrairement à une équation. `floor()` reste chez l'appelant, car c'est lui qui engendre l'événement à chaque front de bit. Validé avant intégration par un modèle `Sandbox` jetable comparant les deux formulations : écart nul à tout instant.
  - `Internal.TwoLineTextIcon` porte les 40 cellules de texte de l'icône 20×2, désormais partagées entre `Peripherals.Display` et `Peripherals.UartLcd20x2`. `Display.mo` passe de 159 Ko à 4,3 Ko. **Vérifié** : l'héritage d'une annotation `Icon` dont les `DynamicSelect` réfèrent à des variables de la classe de base fonctionne dans cette installation d'OMEdit (`verify_12` passe à l'identique).
- **Alternatives envisagées** :
  - **Deux composants distincts** (un pour la requête/réponse, un pour le périodique) — palette OMEdit plus lisible, mais deux bases à maintenir, duplication du câblage UART, et surtout interdiction des appareils mixtes (un GPS qui pousse du NMEA *et* accepte des commandes de configuration est le cas canonique). **Écartée** par l'utilisateur au profit d'un composant unique à deux modes cumulables.
  - **Reconnaissance par correspondance exacte d'une suite d'octets** — la plus simple, mais fragile : une commande fragmentée ou un octet en trop ne correspond plus. **Écartée**.
  - **Reconnaissance par préfixe** — tolérante, mais ambiguë si deux préfixes se chevauchent, et sans notion de fin de commande. **Écartée** au profit du délimiteur, qui est le fonctionnement réel des modules AT.
  - **Valeur mesurée interne simulée** (moyenne + amplitude + période en paramètres, sans connecteur) — aucun câblage à faire, mais impossible de coupler l'appareil à un modèle physique réel. **Écartée** au profit du `RealInput` conditionnel.
  - **Deux tableaux de `String` parallèles** pour la table commande/réponse — structure explicite, mais la saisie d'un tableau de chaînes dans le dialogue OMEdit est pénible. **Écartée** au profit d'une chaîne compacte unique, triviale à passer en `char*` et à redéfinir dans un modèle dérivé.
  - **Connecteur de sortie conditionnel** (`RealOutput valueOut[nOut] if useValueOutput`) — **écartée à l'implémentation** : contrairement à une entrée, une sortie non câblée ne pose aucun problème de détermination, et relier un connecteur de sortie interne à un connecteur de sortie du modèle est le cas délicat du langage. `valueOut` est donc inconditionnel, et `useValueOutput` a disparu de la liste de paramètres.
- **Notes pour plus tard** :
  - **Phase 2 — réalisée : comportement décrit par un script Python.** Le mode `Script` est opérationnel, et **chaque périphérique a son script par défaut** (dossier `Resources/Scripts/Device/`, fichier nommé d'après l'appareil) : basculer `comportement` sur `Script` dans un schéma donne immédiatement un comportement équivalent à la table, sans champ vide à renseigner. `UartLcd20x2` fait exception, par `final comportement = Table` : un afficheur n'a pas de comportement programmable, son rôle est d'afficher ce qu'il reçoit. Ce que le mode apporte, et que la table ne sait pas faire : un **état** (la table associe une commande à une réponse, sans mémoire — cf. `Examples.Uart.StateMachinePy`) et du **calcul** (sommes de contrôle NMEA de `Device/gps.py`, réponses `ERR` aux commandes inconnues de `Device/temperature_sensor.py`).
    - **Chargement** : une fois par **instance**, à la construction de l'External Object, par `PyEval_EvalCode` dans un **dictionnaire de globales qui lui est propre** — surtout pas `PyRun_SimpleString`, qui exécute dans `__main__` et ferait s'écraser mutuellement deux périphériques et le script du MCU. Les variables de module persistent d'un appel à l'autre, et deux instances du même fichier ont deux états indépendants. Une fonction Python transportant ses globales (`__globals__`), aucun équivalent de `g_current` n'est nécessaire : c'est le **sens de l'appel** (C → Python ici, Python → C pour le shim) qui rend la chose gratuite.
    - **Contrat** : trois fonctions facultatives — `on_receive(ligne, t, v)` une fois par ligne complète, `on_tick(t, v)` une fois par période (sa seule présence active l'émission périodique), `outputs()` relue après chaque appel des deux autres et publiée sur `valueOut`. Le **contenu** des trames vient du script, la **temporisation** (`period`, `responseDelay`) reste paramétrée : seuls les deux points de décision du moteur changent de corps, tout le reste (électrique, décodage, ordonnancement, émission) est commun aux deux modes.
    - **Le verrou réel, levé** : le thread worker **conservait le GIL pendant qu'il était garé** dans `SleepConditionVariableCS`, et le thread Modelica l'avait rendu une fois pour toutes. Tout appel Python depuis le thread Modelica se serait bloqué indéfiniment. `yield_to_modelica` (et l'attente initiale de `worker_main`) rendent désormais le GIL pendant l'attente — relâché **avant** d'entrer dans `cs` et repris **après** en être sorti, si bien qu'aucun thread ne tient jamais `cs` en attendant le GIL : pas d'inversion d'ordre de verrous possible.
    - **Démarrage de CPython partagé** (`Resources/Include/pyhost.c`, inclus par les deux chapeaux) : le premier composant construit démarre l'interpréteur, les suivants le trouvent déjà là (`Py_IsInitialized`, garde globale au process même si les deux chapeaux sont compilés séparément). L'ordre de construction des External Objects n'étant pas garanti, les modules C (`_pyruntime_native`, relais `stdout`) sont désormais enregistrés **après** l'initialisation dans `sys.modules`, et non plus par `PyImport_AppendInittab`, utilisable seulement avant. Les dossiers du script et de `libraryPath` sont ajoutés à `sys.path` à l'exécution, dans le même ordre qu'avant. Un périphérique scripté fonctionne donc **sans aucun `MCU`** (vérifié en pré-check).
    - **Garde-fou** : un script de périphérique s'exécute sur le thread Modelica, dans le même interpréteur que celui du MCU. S'il importait `machine` ou `time` et appelait une primitive, celle-ci tenterait de rendre la main à Modelica… depuis le thread Modelica lui-même, et la simulation se figerait sans message. Chaque primitive du shim commence donc par `REQUIRE_WORKER()`, qui transforme ce blocage en exception explicite.
    - **Piège rencontré** : les files d'émission et de réception faisaient 64 octets. Une phrase NMEA RMC en fait 68 — la norme autorise jusqu'à 82 caractères —, si bien que sa fin (somme de contrôle et saut de ligne) était perdue, et que le récepteur ne voyait jamais de ligne complète. Symptôme trompeur : le périphérique journalisait bien ses phrases, le microcontrôleur n'en recevait aucune. Files portées à **256 octets**, de quoi contenir une phrase entière.
    - `print()` dans un script de périphérique est préfixé du nom du composant (`getInstanceName()`, passé au constructeur), et une exception dans un gestionnaire arrête la simulation en nommant le fichier, après avoir rendu le GIL.
  - Restrictions assumées de la table : une commande = une ligne ; `|` et `=>` réservés ; formateur limité à `{vN}`/`{vN:.Pf}` et `{oN}` ; au plus une réponse en attente (une seconde correspondance pendant `responseDelay` est concaténée plutôt que perdue) ; `UARTDEV_MAX_VALUES = 4` grandeurs dans chaque sens.
  - Le débit du périphérique est **le sien**, indépendant de celui du microcontrôleur : un désaccord produit des octets faux. C'est voulu — c'est le symptôme exact d'un désaccord de configuration sur un montage réel, et `Examples.Uart.Lcd` permet de le reproduire sans matériel.
  - Une somme de contrôle NMEA dépasse ce que sait faire la table : en mode Table, `UartGpsModule` émet une trame simplifiée à trois champs ; son script par défaut produit, lui, des phrases RMC complètes.

### Décision : Bus I2C électrique en drain ouvert (`machine.I2C`, `Internal.PartialI2cDevice` et ses dérivés)

- **Contexte** : chantier « Bus I2C » du TODO, ouvert par l'utilisateur le 2026-09-26 après les périphériques série. Cahier des charges tranché via `AskUserQuestion` : un composant « core » dont on hérite pour faire les périphériques, un comportement **uniquement en Python** (pas de table de commandes, contrairement à l'UART), un composant de test type écho (écriture puis lecture) pour valider les trames multi-octets et plusieurs périphériques sur un même bus, puis un écran **Grove - LCD RGB Backlight** (JHD1313 + PCA9633) piloté par un driver MicroPython existant (`driver_lcd_i2c.py`, déposé par l'utilisateur dans `Sandbox/`, sa classe copiée telle quelle dans le module `Resources/Scripts/MCU/driver_grove_lcd_rgb.py`, sa boucle de démonstration dans le programme principal `i2c_grove_lcd_rgb.py` qui l'importe), qui doit tourner **sans modification**.
- **Choix retenu — bus réellement électrique, en drain ouvert** :
  - **Maître (`machine.I2C`, `pyruntime/pyruntime_i2c.c`)** : aucune modification de `MCU.mo`. Le pont GPIO existant suffit : tirer une ligne à la masse, c'est la passer en sortie à l'état bas ; la relâcher, c'est la repasser en entrée (interrupteur ouvert, haute impédance). Le C publie ces deux valeurs pour les deux broches réclamées. La séquence (START, adresse + R/W, bits de poids fort en tête, ACK/NACK, START répété, STOP) avance **par échéances** (`nextWakeTime`), un **quart de période d'horloge** à la fois : SCL basse → SDA positionnée → SCL relâchée → SDA échantillonnée → SCL basse. Une seule action par appel de `PyRuntime_sync`, la suivante toujours strictement dans le futur (condition pour que `time >= pre(nextWakeTime)` se redéclenche). Les broches du bus sont exclues du réveil sur changement d'entrée (`i2c_claimed`, même motif que `uart_rx_claimed`).
  - **Appel bloquant** : `writeto`/`readfrom`/`readfrom_mem`... bloquent le script jusqu'à la fin réelle de la séquence sur le bus, en temps simulé, comme sur le vrai matériel. La primitive `i2c_xfer` arme la transaction puis se gare par `yield_to_modelica(1e300)` ; c'est un drapeau `i2c_done_wake`, posé par le moteur en fin de transaction, qui rend ce réveil « authentique » (sinon il serait pris pour un pitstop de Timer/IRQ). Un appel I2C depuis un callback pendant une transaction lève `OSError(EBUSY)`.
  - **Erreurs, valeurs errno de MicroPython** : adresse non acquittée → `OSError(EIO)` (comme le port rp2) ; ligne restée basse quand elle devrait être libre (vérification du bus avant START, ou SCL relâchée qui ne remonte pas) → `OSError(ETIMEDOUT)`. `scan()` sonde 0x08-0x77 par des écritures vides.
  - **Esclave (`Internal.PartialI2cDevice`, `I2cDeviceImpl.c` + `i2cdevice/`)** : External Object sans thread, comme `UartDevice`. Pont électrique : sur SDA et SCL, un `VoltageSensor` et une capacité d'entrée `CIn` ; sur SDA seulement, un transistor de sortie modélisé par une **conductance variable** (`ROut` quand il tire, `GOff` sinon) — pas de composant `Ideal.*` commutant (piège documenté de la LED embarquée). Décodeur **piloté par les fronts** (`when change(sclBool) or change(sdaBool)`) : START/STOP = SDA qui change pendant que SCL est haute ; un bit est lu au front montant de SCL ; l'esclave positionne SDA (ACK, bit lu) au front descendant de SCL, donc jamais de faux START/STOP. ACK automatique des adresses de la liste et de tout octet écrit ; silence total sur les autres adresses — c'est ce qui permet plusieurs périphériques sur le bus.
  - **Plusieurs acteurs sur un même fil** : le « ET câblé » découle directement de Kirchhoff (chacun ne sait que tirer à la masse). Le TODO « résolution de bus, plusieurs pilotes sur un même fil » est donc résolu **pour l'I2C** par la physique du drain ouvert ; l'UART reste point à point.
  - **Résistances de tirage** : paramètre `usePullUp` du core, **désactivé par défaut** (choix de l'utilisateur), composants conditionnels (`ConstantVoltage` + deux `Resistor`, `RPullUp = 4,7 kΩ`). Le Grove l'active, comme le module réel. Plusieurs paires se mettent en parallèle. Sans aucune paire, les lignes relâchées restent à 0 V (fuite de l'interrupteur ouvert du MCU) et le maître lève `ETIMEDOUT` — le symptôme exact d'un montage où on les a oubliées. Les tirages internes du RP2040 ne sont pas modélisés.
  - **`CIn` n'est pas cosmétique**, même rôle que `CIn` côté UART : elle fait de chaque ligne un état dynamique, ce qui rompt la dépendance entre les `when` du MCU et des esclaves. Valeur par défaut 10 pF (capacité d'entrée typique) : temps de montée 4,7 kΩ × 10 pF = 47 ns, loin du quart de période à 400 kHz (625 ns). Plusieurs périphériques = plusieurs capacités **en parallèle sur le même nœud** : OpenModelica 1.27.1 le gère sans difficulté (vérifié par `verify_22`, trois esclaves).
  - **Contrat Python au niveau transaction** (choix de l'utilisateur) — le script ne voit ni bits, ni START/STOP, ni ACK : `on_write(addr, data, t, v)` à la clôture d'une phase d'écriture (STOP ou START répété ; jamais pour une écriture vide, donc les sondes de `scan()` sont invisibles) ; `on_read(addr, t, v)` à l'entrée en lecture, octets sortis un par un, rappelée si le maître en veut plus (`0xFF` si rien) ; `outputs()` → `valueOut` ; `lines()` facultative → `line1`/`line2` (afficheurs). `addr` est passé car un composant peut avoir **plusieurs adresses** (`addresses`, chaîne `"0x3E, 0x62"` : Modelica n'a pas de littéraux hexadécimaux).
  - **Mécanique Python commune extraite** : chargement dans un espace de noms propre, prélude `print` préfixé, conversions, arrêt propre sur exception vivent désormais dans `Resources/Include/devscript.c`, partagé par `uartdevice_script.c` (qui n'en garde que son contrat) et `i2cdevice_script.c`.
  - **Écran Grove** (`Peripherals.I2cGroveLcdRgb`, script `Device/grove_lcd_rgb.py`) : émulation d'après les fiches techniques, sans connaissance du driver — JHD1313 (octet de contrôle Co/RS, jeu de commandes HD44780, DDRAM 2 × 40 et compteur d'adresse, écran éteint à la mise sous tension, octets ignorés avec avertissement pendant un effacement de 1,52 ms) et PCA9633 (registres, auto-incrément, `LEDOUT`, veille de l'oscillateur, gradation de groupe). Icône dédiée `Internal.Lcd16x2RgbIcon` (32 cellules générées mécaniquement, fond à la couleur du rétroéclairage). **Validé** : le driver de l'utilisateur tourne tel quel (`Examples.I2c.GroveLcd`, `verify_24`). Le shim accepte pour cela `I2C(scl=..., sda=..., freq=...)` sans identifiant, en plus de la forme rp2 `I2C(0, ...)`.
- **Point dur trouvé à l'implémentation, et corrigé** : l'esclave comptait les coups d'horloge au front **descendant** de SCL — or le premier front descendant après un START n'est pas un coup d'horloge de donnée. Il ne capturait que 7 bits et lisait `0x42` au lieu de `0x84` : aucune adresse n'était acquittée. Les impulsions se comptent désormais au front **montant**, le front descendant ne sert qu'à positionner SDA pour le bit suivant.
- **Alternatives envisagées** :
  - **Bus logique (transactions livrées d'un bloc, connecteur causal type `Display`)** — bien plus simple et rapide, mais aucune trame visible et un « multi-périphérique » réduit à un aiguillage d'adresse en C. **Écartée** par l'utilisateur.
  - **Tirages dans un composant bus dédié, ou dans le MCU** — écartés au profit d'un paramètre du core, désactivé par défaut (choix de l'utilisateur), plus proche des modules du commerce qui les portent.
  - **Contrat Python au niveau octet** (`on_start`/`on_byte`/`on_read_byte`/`on_stop`) — plus proche du matériel (NACK sélectif possible), mais verbeux pour chaque périphérique. **Écarté** ; à reconsidérer si un périphérique doit refuser un octet.
  - **Mettre tous les composants en threads** (proposition de l'utilisateur, en vue du multi-instance) — **écartée après discussion** : un thread ne sert qu'à garder en vie un programme suspendu ; un périphérique réactif n'a rien à suspendre, et le passer en thread coûterait deux changements de contexte par événement, sans parallélisme possible (Modelica attend chaque `when`, GIL unique), en multipliant la partie la plus fragile du projet (protocole de synchro, 5 pièges documentés). Principe retenu : **un thread par programme, pas par composant** — cf. décision « Multi-instances ».
- **Notes pour plus tard** :
  - Pas de clock stretching (une SCL tenue basse par un esclave est une erreur `ETIMEDOUT`, pas une attente), pas d'arbitrage multi-maître, un seul bus (`I2C(0)` ; `I2C(1)` accepté comme alias), fréquence bornée à 1 kHz - 1 MHz, 256 octets au plus par transaction, un esclave acquitte toujours ses octets.
  - `SoftI2C` est un alias de `I2C` : en simulation, maître logiciel et matériel ne se distinguent pas.
  - **I2C esclave côté microcontrôleur** : TODO, suppose un second `MCU` sur le bus, donc le multi-instance.
  - Le Grove v5 réel remplace le PCA9633 par un autre driver de LED à une autre adresse ; le composant suit le PCA9633 à `0x62`, cible du driver de référence.

La bibliothèque fournit un fichier de démonstration par défaut dans son arborescence (ex. `Resources/Scripts/MCU/demo.py`), utilisé comme valeur par défaut du paramètre, pour qu'un modèle fraîchement déposé fonctionne sans configuration.

### Décision : Import de modules auxiliaires (dossier du script / bibliothèque partagée)

- **Contexte** : principe directeur donné par l'utilisateur pour évaluer tout ajout au projet — simple et ergonomique pour un élève pressé, sans sacrifier la richesse/souplesse du système. Aujourd'hui, `import mon_module` échoue si `mon_module.py` est à côté du script principal : le script est chargé par `fopen`/`fread` puis exécuté via `PyRun_SimpleString` (un `exec()` de chaîne, pas un vrai run de fichier), et `sys.path` ne contient que `<pythonHome>/python312.zip` et `<pythonHome>` (`config.module_search_paths_set = 1`, configuré une fois dans `PyRuntime_new`) — le dossier du script n'y est pas.
- **Choix retenu** : deux nouveaux paramètres sur `MCU`, regroupés avec `scriptPath` dans la boîte de dialogue OMEdit (`Dialog(group = "Script Python")`) :
  - `addScriptDirToPath` (`Boolean`, **`true` par défaut**) : ajoute le dossier de `scriptPath` au chemin de recherche des modules Python. Reproduit le comportement du vrai Pico (le dossier racine du système de fichiers flash est déjà sur `sys.path`) — zéro-config pour le cas le plus courant (élève qui pose `helper.py` à côté de son script).
  - `libraryPath` (`String`, vide par défaut = désactivé) : désigne un fichier `.py` d'un dossier de bibliothèque partagée (ex. fourni par l'enseignant) ; c'est le **dossier contenant ce fichier** qui est ajouté au chemin de recherche. Cas plus avancé, opt-in.
  - Propagation : `MCU.mo` (site d'instanciation de `Internal.PyRuntime`) → `Internal/PyRuntime.mo` (2 nouveaux `input` du constructeur) → `PyRuntimeImpl.c`, `PyRuntime_new` (fonction utilitaire `dirname_of()`, ajoute 0-2 entrées de plus au même `PyWideStringList` que le zip/pythonHome déjà en place — aucun changement structurel).
- **Limitation découverte en recherchant la documentation des annotations reconnues par OpenModelica** (package `ModelicaReference`, et recherche dans toute la bibliothèque `Modelica 4.0.0` installée) : l'annotation `Dialog` standard Modelica ne propose que `loadSelector`/`saveSelector` (sélecteurs de **fichier**) et `colorSelector` — pas de sélecteur de **dossier** (`directorySelector` ou équivalent introuvable). **Conséquence** : `libraryPath` utilise lui aussi un `loadSelector` (bouton « ... », filtre `*.py`, cohérent avec la formulation de la demande de l'utilisateur) plutôt qu'un vrai sélecteur de dossier — solution pragmatique dans la limite de ce que l'outil permet.
- **Alternatives envisagées** :
  - `sys.path.append(...)` codé en dur dans le script utilisateur lui-même — ne demande aucun changement du runtime, mais chemin absolu non portable, à retaper dans chaque script. Écarté comme solution par défaut (trop peu ergonomique pour l'objectif visé), reste possible en complément pour un besoin ponctuel.
  - Un mécanisme d'`#include` maison (concaténation de fichiers avant `exec`) — écarté : non standard, casserait la portabilité MicroPython du script (contrainte clé du projet, cf. section Besoin).
- **Notes pour plus tard** :
  - **Effet de bord (transparence, pas un problème constaté)** : les scripts des exemples fournis par la bibliothèque partagent tous `Resources/Scripts/` — avec `addScriptDirToPath = true` par défaut, ils deviennent mutuellement capables de s'importer entre eux. Sans conséquence aujourd'hui (aucun ne le fait), simple changement du modèle d'isolation à garder en tête si un futur exemple venait à nommer un fichier de la même façon qu'un autre.
  - Si le besoin d'ajouter plusieurs bibliothèques partagées distinctes se présente, étendre `libraryPath` (aujourd'hui un seul champ) plutôt que d'en ajouter un troisième dès maintenant — pas fait en v0, complexité non justifiée pour l'instant.
  - **Vérifié empiriquement** (`Examples.ImportDemo`, `verify_09_import.mos`) : un script important à la fois un module posé à côté de lui (`addScriptDirToPath`) et un module d'un dossier séparé (`libraryPath`) fonctionne du premier coup, sans bissection nécessaire.

### Décision : Nettoyage du schéma interne de `MCU` et simplification du câblage des exemples

- **Contexte** : retour utilisateur après usage — le schéma interne (`Diagram`) de `MCU` (pont électrique par broche : `src`/`rOut`/`sw`/`sns`/`ledResistor`/`rt`, cf. décision « Domaine électrique vs logique pur ») est jugé « trop brouillon » une fois affiché dans OMEdit, et les résistances de tirage systématiques sur les broches GPIO inutilisées des exemples sont jugées incohérentes (« Ça n'a pas de sens » de tirer artificiellement à la masse une broche qui n'est reliée à rien).
- **Choix retenu (schéma interne)** : tous les composants internes du pont GPIO (`rt`, `src[9]`, `rOut[9]`, `sw[9]`, `sns[9]`, `ledResistor`) ainsi que `builtinLed` passent en `Placement(visible = false, ...)`, et les annotations `Line(...)` de leurs `connect()` sont retirées — le schéma interne de `MCU` est donc volontairement vide en v0 (seuls les 8 connecteurs `GPx` + `GND` restent visibles, sans aucun câblage affiché). Un schéma interne propre et lisible est reporté à plus tard (« on verra plus tard »), plutôt que de investir du temps dans un routage manuel immédiatement. Aucun changement fonctionnel : uniquement des annotations cosmétiques (`visible`/`Line`), aucune équation touchée — `checkModel` confirme 397 équations/397 variables inchangées.
- **Choix retenu (câblage des exemples)** : les résistances de tirage (« pulldown ») sur les broches `GPx` non utilisées par le script d'un exemple sont supprimées ; ces broches sont simplement laissées non connectées. Retesté empiriquement sur les 9 scénarios de vérification, y compris `PinEcho` (le cas le plus à risque, cf. piège 3a ci-dessus, section « Domaine électrique vs logique pur ») — tout passe sans régression. Concerne `BasicBlink`, `SleepCompression`, `InputReactivity`, `ScriptError`, `PinEcho`, `AdcRead`, `PwmLed`, `PwmLedFade`, `ImportDemo` (`LedChaser` utilise déjà ses 8 broches, non concerné).
- **Choix retenu (`BasicBlink`)** : la broche `GP0`, jusque-là chargée par une simple résistance (`Resistor led(R=1000)`, pas de composant visuel réactif), reçoit désormais une vraie `Peripherals.LED` (`led0`, motif `r0`(330 Ω)+`led0` déjà utilisé par `AdcRead`/`PwmLed`/`ImportDemo`) — cohérent avec les autres exemples et visuellement réactif pendant la lecture animée d'un résultat. Le script par défaut (`demo.py`) pilotait déjà `Pin(0)` et `Pin(Pin.LED)` ensemble (`led.on()`/`builtin.on()` dans la même itération) : `led0` et la LED embarquée de `mcu` clignotent donc déjà en phase, sans changement de script nécessaire.
- **Alternatives envisagées** : redessiner proprement le schéma interne de `MCU` immédiatement (composants repositionnés, fils routés) plutôt que le vider — écarté pour l'instant, jugé plus coûteux que la valeur immédiate pour la v0 ; l'option reste ouverte plus tard (ce paragraphe documente l'intention).
- **Notes pour plus tard** : si `MCU.mo` est modifié substantiellement (nouveau composant interne, etc.), redessiner un schéma interne lisible plutôt que de se contenter du vide actuel. Si une nouvelle électronique interne devait un jour reproduire la singularité du piège 3a (broches flottantes + bouclage), le motif `pulldown` reste documenté ci-dessus comme filet de secours.

**Convention de placement actuelle des `Examples/*.mo`** : chaque composant utilise `origin = {cx, cy}` avec un `extent` symétrique et carré (ex. `origin = {-90, 25}, extent = {{-15,-15},{15,15}}`) — corrigé après trois défauts visuels trouvés en relecture (marqueur d'origine décalé, `mcu` démesuré par rapport aux autres composants, icônes aplaties). Norme à suivre pour tout nouvel exemple. Détail des trois défauts et de leur correction : `requirements-archive.md`.

### Décision : LED embarquée (GP25) — traitée comme une broche normale, avec un vrai pont électrique interne

- **Contexte** : sur le vrai Raspberry Pi Pico, une LED est câblée en dur sur `GP25`, non reliée à une broche externe du connecteur — elle n'est donc pas l'une des 29 broches GPIO générales de la carte. Demande initiale : afficher une pastille verte sur l'icône (cosmétique). Demandes de suivi successives : la rendre réellement pilotable depuis le script comme sur la vraie carte, puis la traiter « comme une broche normale » plutôt qu'un cas particulier booléen — cf. discussion et choix tranchés via `AskUserQuestion` (garder le numéro 25 ; ajouter un vrai pont électrique interne réutilisant les composants GPIO).
- **Choix retenu (version actuelle)** : un 9ᵉ canal interne (index 8 côté C, `pinBoolIn`/`pinBoolOut`/`pinIsOutput` passent de taille 8 à 9), traité par le même protocole `PyRuntime_sync` que les 8 GPIO (même thread worker, même mécanisme de synchro/compression de `sleep`) **et par le même pont électrique** (`SignalVoltage`/`Resistor`/`IdealOpeningSwitch`/`VoltageSensor`, tableaux étendus à 9 éléments, boucle `for i in 1:9`) — mais **sans connecteur externe** : la sortie de ce pont interne (indice 9) alimente à demeure une résistance série dédiée (`ledResistor`, paramètre `ledSeriesR`, 330 Ω par défaut) puis une vraie instance de `Peripherals.LED` (`builtinLed`) reliée à `GND`, fidèle au câblage réel du Pico. `pinBoolIn[9]` n'est donc plus une constante `false` : c'est une vraie mesure de tension au même titre que les 8 autres broches, comparée aux mêmes seuils `VIL`/`VIH` — la broche « relit » ainsi son propre état comme une broche normale. Côté C, `resolve_pin_index()` fait toujours correspondre l'identifiant `25` écrit dans le script à cet index 8 (les identifiants 0-7 restent mappés tels quels).
- **Ancienne version (superseded)** : la toute première implémentation n'avait ni connecteur électrique ni pont GPIO pour ce canal (juste une valeur booléenne relayée à l'icône) — remplacée par le pont électrique ci-dessus. Détail : `requirements-archive.md`.
- **Alternatives envisagées** :
  - Rester purement cosmétique (pastille statique, non pilotable) — c'était la toute première version.
  - Exposer `GP25` comme un vrai connecteur électrique **externe** au même titre que `GP0`-`GP7` — écarté : infidèle au matériel réel (la LED embarquée n'est pas reliée à une broche externe sur le Pico) et aurait mélangé une broche « interne dédiée » avec les broches générales.
- **Piège 1 (variables `protected` invisibles dans les résultats)** : la variable/les blocs qui alimentent l'animation de l'icône (`DynamicSelect`) doivent être **publics**, pas `protected` — dans cette installation OpenModelica, les variables/composants `protected` n'apparaissent pas dans les résultats de simulation par défaut (vérifié empiriquement : même `pinNodeVoltage`, pourtant utilisée dans une vraie équation électrique, est absente des résultats), donc l'animation afficherait une couleur figée. Rencontré une première fois sur `Peripherals.LED` (variable `brightness`), puis à nouveau sur `MCU` (`ledOn`/`ledMean` de l'ancienne version) avant que la vraie cause soit identifiée. Le reste de l'implémentation (ponts GPIO, `PyRuntime`, tableaux `pinBool*`) reste `protected` comme avant ; seul `builtinLed` (et son `mean` interne, public via `Peripherals.LED`) est public dans `MCU`, par exception nécessaire à l'animation.
- **Piège 2 (composants `Ideal.*` à éviter dans un sous-circuit inactif longtemps)** : `Modelica.Electrical.Analog.Ideal.IdealDiode` (composant à structure variable) laissé en régime « bloqué » pendant une longue simulation à tick périodique a fini par perturber le mécanisme `when`/`pre(nextWakeTime)` qui pilote la compression des `sleep`, bloquant silencieusement le thread worker — y compris pour des broches sans rapport avec la LED embarquée, sans aucune erreur remontée par `checkModel`/`simulate`. Remplacé par `Modelica.Electrical.Analog.Semiconductors.Diode` (caractéristique exponentielle lisse, pas de bascule structurelle) dans `Peripherals.LED`, ce qui supprime totalement le problème. Récit de la bissection qui a isolé la cause : `requirements-archive.md`.
- **Notes pour plus tard** : si d'autres icônes réactives sont ajoutées, garder le piège 1 en tête. Pour toute future extension électrique du projet, éviter les composants `Ideal.*` à structure variable dans un sous-circuit qui peut rester longtemps dans un état non sollicité au sein d'une simulation à événements fréquents (piège 2) — préférer une caractéristique lisse type `Semiconductors.*` sauf besoin explicite de la commutation idéale. Si `GP25` doit un jour devenir configurable (numéro de broche différent selon variante de carte), remplacer la constante `LED_PIN_ID=25` par un paramètre.

### Décision : Calibration de la luminosité de l'icône `Peripherals.LED` (`IMax`, fenêtre de lissage)

- **Contexte** : retour utilisateur après usage — la couleur de l'icône n'atteignait jamais vraiment `colorOn` (rouge vif) même LED allumée en régime établi, et le clignotement rapide (ex. chenillard `LedChaser`, ~150 ms/broche) apparaissait flou/peu visible pendant la lecture animée d'un résultat.
- **Choix retenu** :
  - `IMax` (courant correspondant à la luminosité maximale sur l'échelle d'affichage) abaissé de `0.006` (6 mA) à `0.0035` (3,5 mA) — la valeur précédente était supérieure au courant réellement atteignable avec le câblage typique du projet (résistance série 330 Ω, `VOH`=3,3 V, `ROut`=100 Ω interne), donc l'icône plafonnait à ~58 % de `colorOn` même à pleine luminosité réelle.
  - Fenêtre de `Modelica.Blocks.Math.Mean` réduite de `f=10` (100 ms) à `f=50` (20 ms) — une fenêtre de lissage longue par rapport à la cadence de clignotement dilue le pic de courant mesuré et floute les transitions ; 20 ms reste largement inférieur au clignotement le plus rapide du projet (150 ms/broche) tout en amortissant le bruit numérique de la simulation.
- **Alternatives envisagées** : rendre `IMax`/`f` dépendants du courant nominal effectivement calculé (fonction de `ledSeriesR`) — écarté pour la v0, complexité non justifiée face à un simple recalibrage des valeurs par défaut ; ces deux paramètres restent modifiables par instance si un câblage différent est utilisé.
- **Notes pour plus tard** : si `ledSeriesR` (ou une résistance série externe dans un schéma utilisateur) change significativement, `IMax` peut nécessiter un nouveau recalibrage pour rester représentatif du courant réellement atteint.

### Décision : Structure du package et interface C du runtime Python

- **Choix retenu** : la structure du package et la signature C de `PyRuntime_sync` évoluent à chaque extension (ADC, PWM, IRQ/Timer, Display...) en ajoutant des tableaux/paramètres similaires plutôt qu'en changeant la structure d'ensemble — principe validé par toutes les extensions faites jusqu'ici. **Documentation à jour de la structure actuelle** : `CLAUDE.md` et `docs/architecture.md`, tenus à jour à chaque évolution (pas dupliqué ici pour éviter la dérive entre deux copies).
- **Rangement de `Resources/Include/` (fait)** : les en-têtes CPython 3.12 vendorés (76 entrées, dont les sous-dossiers `cpython/` et `internal/`) vivent désormais dans `Resources/Include/cpython312/` ; la racine d'`Include/` ne contient plus que nos propres fichiers (`PyRuntimeImpl.c`, `PyRuntimeImpl.h`, `StringToCharCodes.c`, plus le dossier `pyruntime/` ci-dessous), soit 5 entrées au lieu de 79. **La contrainte redoutée n'existe pas** : on supposait qu'il faudrait ajouter un chemin d'inclusion au compilateur, les en-têtes de CPython s'incluant entre eux sans préfixe. Mais ils le font en include *quoted* (`#include "object.h"`), et un include quoted est résolu **d'abord relativement au dossier du fichier qui l'inclut** — donc depuis `cpython312/`. Il a suffi d'écrire `#include "cpython312/Python.h"` (guillemets, pas chevrons) dans `PyRuntimeImpl.c` : `IncludeDirectory` reste `Resources/Include` sur les trois annotations, aucun flag ajouté. Vérifié d'abord en isolation (`gcc -c` sur un fichier sonde compilé depuis le dossier parent, reproduisant exactement l'imbrication), puis par les 13 scénarios.
- **Découpage de `PyRuntimeImpl.c` (fait)** : le fichier (1291 lignes après l'extraction du shim) est devenu un **fichier chapeau** de ~45 lignes qui inclut textuellement 8 parties thématiques dans `Resources/Include/pyruntime/` : `pyruntime_core.h` (constantes + `struct PyRuntimeHandle` + handle courant), `_relay.c` (stdout/stderr), `_sync.c` (dispatch des callbacks + `yield_to_modelica`), `_pin.c` (`Pin`/`ADC`/`PWM`/`irq` + `sleep`/`ticks`), `_display.c`, `_uart.c`, `_timer.c`, `_module.c` (table des natives, thread worker, API exportée). Option « chapeau » retenue plutôt qu'une vraie compilation séparée : une seule unité de compilation, donc **aucun changement d'annotation `Include`/`Library` et aucune étape de build ajoutée** à un projet qui n'en a aucune. **Conséquence à connaître pour toute évolution** : l'ordre des inclusions dans le chapeau est significatif (chaque `static` doit être défini avant son premier appel) — il suit les dépendances réelles (cœur de synchro avant les primitives natives qui l'appellent, périphériques avant la table des méthodes et l'API exportée), ce qui a permis de se passer entièrement de prototypes croisés. Le découpage a été fait par extraction mécanique de plages de lignes (contenu inchangé, aucune retranscription), et a compilé du premier coup.
- **Notes pour plus tard** : une proposition initiale (jamais implémentée, domaine `Digital` puis classe `Pico`) et un snapshot de la structure aux jalons M0-M11 sont conservés dans `requirements-archive.md` pour l'historique. Ajouter un périphérique (I2C, SPI...) consiste maintenant à ajouter un `pyruntime_<periph>.c` et une ligne dans le chapeau, à la bonne place dans l'ordre des inclusions. La vraie compilation séparée (objets précompilés référencés par `Library`) reste l'option de repli si une seule unité de compilation devenait un jour gênante — pas le cas aujourd'hui.

### Décision : Distribution Python embarquée (portabilité vers un autre poste)

- **Contexte** : question soulevée en cours de session — l'approche initiale (compiler/lier contre le Python installé sur la machine de développement) obligerait chaque poste élève à avoir Python 3.12 installé à un emplacement connu, ce qui est une vraie friction en contexte scolaire (postes multiples, pas forcément de droits admin).
- **Choix retenu** : la bibliothèque embarque la distribution Python officielle « embeddable » (zip `python-3.12.4-embed-amd64.zip` distribué par python.org, prévu justement pour ce cas d'usage — appli qui embarque Python sans installateur ni entrée registre) dans `Resources/PythonRuntime/`. Ça élimine le prérequis « installer Python » côté élève. Seul prérequis résiduel sur le poste cible : le VC++ Redistributable (la DLL officielle est compilée MSVC), quasi toujours déjà présent. Les binaires (DLL + stdlib zip, quelques Mo) sont committés directement dans le dépôt (simplicité > légèreté du dépôt pour la v0).
- **Alternatives envisagées** :
  - Garder un Python système requis — écarté : friction réelle en contexte scolaire, cf. contexte ci-dessus.
  - Script de récupération du zip « embeddable » au premier build plutôt que de committer les binaires — plus propre pour un dépôt git mais ajoute une dépendance réseau/une étape supplémentaire ; écarté pour la v0, à reconsidérer si la taille du dépôt devient gênante.
- **Détails d'implémentation qui découlent de ce choix** :
  - `PyRuntime_new` reçoit un `pythonHome` (résolu via `Modelica.Utilities.Files.loadResource`, comme `scriptPath`) plutôt qu'un chemin codé en dur — la portabilité est donc automatique, ce n'est plus une limitation v0 à documenter comme envisagé un temps.
  - La distribution « embeddable » range le stdlib dans `python312.zip` (pas de dossier `Lib`/`DLLs` dépliés comme une install normale) : il a fallu configurer explicitement `config.module_search_paths` (zip + dossier home) plutôt que de laisser CPython deviner ses chemins — sinon le calcul automatique se fait polluer par une éventuelle installation Python système via le registre Windows (observé en session : `sys.path` pointait vers le Python système au lieu du Python vendoré, malgré `PYTHONHOME` positionné).
  - Une bibliothèque d'import compatible MinGW (`libpython312.a`) a dû être régénérée (`gendef`+`dlltool`, déjà présents dans le toolchain d'OpenModelica) à partir de la DLL vendorée, car seule la version MSVC (`python312.lib`) est fournie par la distribution embeddable/l'installation système.
  - **Résolution de `python312.dll` à l'exécution** : pour la v0, on s'appuie sur un lien classique (`-lpython312`) : la DLL doit être trouvable au démarrage du process de simulation généré (à côté de l'exécutable, ou sur le PATH). Un chargement dynamique explicite (`LoadLibrary` résolu au chemin de ressource Modelica, indépendant de l'ordre de recherche de DLL de l'OS) serait plus robuste mais plus coûteux à développer — cf. TODO.
- **Notes pour plus tard** : n'a pas encore été testé sur un poste sans Python système du tout (la machine de développement en a un, utilisé seulement pour ses en-têtes de compilation `Python.h`, vendorés eux aussi dans `Resources/Include/` — pas pour l'exécution, vérifié en désactivant le Python système du PATH pendant les tests). À valider en conditions réelles sur un poste élève.

### Décision : Multi-instances (plusieurs microcontrôleurs dans un même modèle)

- **Choix retenu** : une seule instance de microcontrôleur en v0. Pas de sous-interpréteurs CPython pour cette version.
- **Alternatives envisagées** :
  - Support multi-instances dès la v0, via des sous-interpréteurs CPython (`Py_NewInterpreter`) pour isoler l'état (`sys.modules`, etc.) de chaque script — écarté : complexité disproportionnée pour une preuve de concept, et CPython embarque mal plusieurs interpréteurs vraiment isolés (verrou global GIL, état de modules partagé par défaut).
- **Notes pour plus tard** : le multi-instances nécessitera l'isolation par sous-interpréteur (chaque instance avec son propre état de modules, en évitant tout singleton global dans le shim `machine`/`time`).
  - **Blocages identifiés précisément (2026-09-26)** : (1) `g_current`, pointeur **global** (`pyruntime_core.h`) par lequel chaque primitive native retrouve « son » microcontrôleur ; (2) un **espace de noms Python unique** — le shim s'installe dans `sys.modules['machine']`, commun au process, et le script tourne dans `__main__` (`PyRun_SimpleString`) : deux MCU partageraient `machine`, leurs globales et leurs modules importés. Chaque MCU ayant **déjà** son propre thread worker, le remède n'est pas « plus de threads » mais : `g_current` en stockage local de thread (un worker = un thread), et un **sous-interpréteur par MCU** (`Py_NewInterpreterFromConfig`, présent dans les en-têtes 3.12 vendorés, GIL propre possible), le module natif passant en initialisation multi-phase. Le code du maître I2C a été écrit en conséquence : ses fonctions internes prennent le handle en paramètre, seules les natives lisent `g_current`.
  - **Alternative discutée et écartée : tous les composants en threads** (proposition de l'utilisateur, 2026-09-26). Un thread ne sert qu'à garder en vie un programme suspendu en plein milieu ; les périphériques réactifs n'ont rien à suspendre, et les threads n'apporteraient ni parallélisme (Modelica attend chaque `when`, GIL unique) ni simplicité (aller-retour de threads à chaque événement, protocole de synchro multiplié). Principe retenu : **un thread par programme, pas par composant** — un périphérique qui exécute un vrai programme (esclave I2C tournant sur un microcontrôleur, capteur « intelligent » avec son firmware) sera une instance de `MCU`, d'où l'intérêt du multi-instance.

### Décision : Comportement en cas d'exception non gérée dans le script

- **Choix retenu** : arrêt de la simulation, avec la trace Python (traceback) remontée comme erreur Modelica claire et lisible pour l'utilisateur.
- **Alternatives envisagées** :
  - Figer les sorties GPIO à leur dernière valeur et laisser le reste de la simulation continuer (mime un crash matériel réaliste) — écarté : moins pédagogique, plus difficile à diagnostiquer pour un élève.
- **Notes pour plus tard** : le mode « figer et continuer » pourrait redevenir pertinent dans une version orientée réalisme industriel, au-delà du cadre pédagogique actuel.

**Implémenté** : `PyRun_SimpleString` affiche elle-même la trace via `sys.stderr` (relayée vers `ModelicaFormatMessage`) avant de rendre la main en cas d'échec — un simple code de retour déclenche `ModelicaError`. Retenue après qu'une première approche (récupération manuelle de la trace via `PyErr_Fetch`) s'est avérée provoquer un plantage systématique dans le contexte de l'exécutable généré par OpenModelica — écueil détaillé dans `requirements-archive.md`. **Limitation connue** : le nom de fichier affiché dans la trace est `<string>`, pas le vrai chemin du script (cf. TODO).

### Décision : Protection contre un script qui ne rend jamais la main

- **Choix retenu** : aucune protection/timeout en v0 (le risque de blocage de la simulation est accepté). Principe de conception retenu dès maintenant : tout appel à une API surchargée du shim (`machine.*`, `time.*`) doit être un point de synchronisation potentiel avec Modelica — pas seulement `sleep()`. Ce point de passage unique facilite l'ajout ultérieur d'une protection, même si une boucle strictement CPU-bound sans aucun appel au shim resterait indétectable par ce mécanisme.
- **Alternatives envisagées** :
  - Timeout configurable dès la v0, avec arrêt en erreur si le script ne se synchronise pas dans un délai donné — écarté pour la v0, à reconsidérer pour la version exhaustive.
- **Notes pour plus tard** : implémenter un timeout mou basé sur ce principe (vérification du temps réel écoulé à chaque appel au shim) pour la version exhaustive.

**Précision issue de l'implémentation** : le principe est concrètement réalisé par `Pin.__init__`/`.value()`/`.on()`/`.off()` et `time.sleep*`, qui rendent tous la main à Modelica (cf. décision shim `machine`/`time`, section « raffinement »). `time.ticks_ms()`/`ticks_us()` ont été délibérément exclus de ce principe (lectures pures, pas de synchro) — une boucle de polling non bloquante basée uniquement sur `ticks_ms()` sans jamais lire/écrire de broche ni dormir échapperait donc à ce mécanisme, comme une boucle purement CPU-bound. Cas marginal, cohérent avec l'absence de protection acceptée pour la v0.

### Décision : Cycle de vie du script lors d'une relance (reset) de la simulation

- **Choix retenu** : chaque relance de la simulation recrée l'External Object depuis zéro ; le script redémarre intégralement, comme un power-cycle d'un vrai microcontrôleur.
- **Alternatives envisagées** :
  - Conserver l'état Python entre les relances — écarté : moins fidèle au comportement d'un vrai microcontrôleur, complexité inutile.
- **Notes pour plus tard** : comportement cohérent avec le cycle de vie standard (constructeur/destructeur) d'un External Object Modelica, pas d'action spécifique à prévoir.

**Implémenté et validé** : deux relances successives du même scénario produisent des résultats identiques — chaque relance exécute l'exécutable de simulation généré comme un nouveau process OS, le redémarrage « à zéro » est donc une conséquence naturelle de l'architecture (pas de mécanisme de reset explicite à coder). Détail de la vérification : `requirements-archive.md`.

### Décision : Sortie des print() et des erreurs du script

- **Choix retenu** : rediriger `stdout`/`stderr` du script Python vers les messages OpenModelica (`ModelicaFormatMessage`/`ModelicaError`), pour qu'ils apparaissent directement dans le journal de simulation d'OMEdit — même endroit que les erreurs d'exécution (cf. décision sur les exceptions non gérées), sans fenêtre supplémentaire à chercher.
- **Alternatives envisagées** :
  - Fichier de log séparé à côté du script — garde le journal de simulation « propre » si le script produit beaucoup de sortie, mais moins immédiat pour l'élève (fichier à ouvrir manuellement). Écarté pour la v0.
  - Les deux en parallèle — plus complet mais plus de travail d'implémentation dès la v0. Écarté pour la v0.
- **Notes pour plus tard** : si le volume de sortie devient gênant dans le journal de simulation (scripts très verbeux), reconsidérer un fichier de log séparé en complément.

**Implémenté** : les caractères écrits sur `stdout`/`stderr` s'accumulent côté C (`relay_emit_pending` dans `PyRuntimeImpl.c`) jusqu'à un vrai `\n`, un seul appel à `ModelicaFormatMessage` par ligne complète (le buffer est aussi vidé explicitement à la fin du script, pour ne pas perdre une dernière ligne sans saut de ligne final). Retenu après qu'un `print()` à plusieurs arguments s'est avéré éclater sur plusieurs lignes de journal — défaut et correction détaillés dans `requirements-archive.md`.

## Restrictions version 0

*Lister ici les limitations volontairement acceptées pour une v0 dont le seul but est de démontrer que ça peut marcher (preuve de concept). Périmètre réduit assumé, pas encore la version cible.*

- Le microcontrôleur simulé expose des GPIO simples (entrées/sorties numériques), l'ADC (`machine.ADC`, lecture 16 bits), le PWM (`machine.PWM`), les interruptions sur broche (`machine.Pin.irq`), les minuteurs logiciels (`machine.Timer`), une liaison série électrique réelle (`machine.UART`, cf. ci-dessous), un bus I2C électrique en drain ouvert (`machine.I2C`, maître uniquement, cf. ci-dessous) et une liaison logique vers un périphérique d'affichage pédagogique (`machine.Display`, écriture seule — pas un protocole). Pas de SPI pour cette version.
- `machine.UART` : un seul périphérique (`UART(0)`), broches TX/RX au choix parmi `GP0`-`GP7` (deux broches distinctes obligatoires), **format de trame 8N1 figé** — `bits`/`parity`/`stop` acceptés pour compatibilité d'API mais sans effet, comme `pull=` sur `Pin`. Débit borné à 50-115200 bauds (garde-fou contre une tempête d'événements, un événement Modelica étant généré par front de bit), 1200 bauds par défaut. Files d'émission et de réception de 256 octets : un débordement perd silencieusement les octets excédentaires (comme un FIFO matériel), et une trame dont le bit de stop n'est pas au niveau haut est ignorée sans remontée d'erreur de framing. Pas de `uart.irq()` (la réception ne réveille pas le script, qui récupère les octets par `any()`/`read()`), pas de contrôle de flux RTS/CTS. Une broche affectée à la réception UART ne génère plus d'interruption GPIO ni ne réveille un `sleep()` en cours — fidèle au matériel, et indispensable au fonctionnement (cf. décision « UART électrique réel »). Cf. décision « UART électrique réel ».
- Périphériques série externes (`Internal.PartialUartDevice` et ses dérivés) : **une commande = une ligne**, terminée par `terminator` ; les suites `|` et `=>` sont **réservées** par le format de la table et ne peuvent apparaître ni dans une commande ni dans une réponse. Le formateur ne connaît que `{vN}`, `{vN:.Pf}` (substitution d'une grandeur du modèle dans une trame émise) et `{oN}` (capture d'un nombre d'une trame reçue vers une sortie réelle) — pas de conditionnelle, pas de boucle, pas de somme de contrôle : tout besoin qui dépasse ce cadre relève du mode `Script` (phase 2, pas encore disponible). Au plus **une réponse en attente** à la fois : une seconde correspondance survenant pendant `responseDelay` est concaténée à la première plutôt que perdue. Quatre grandeurs au maximum dans chaque sens (`UARTDEV_MAX_VALUES`). Le débit du périphérique est le sien, indépendant de celui du script — un désaccord produit des octets faux, ce qui est voulu. En mode `Script`, les gestionnaires s'exécutent sur le thread de la simulation : **pas de `sleep()`, pas d'accès à `machine`/`time`** (exception explicite), **un fichier autonome** (le dossier du script n'est pas ajouté à `sys.path`), et une charge utile tronquée au-delà de 127 octets. Cf. décision « Périphériques UART externes connectables ».
- `machine.I2C` : **maître uniquement** (pas d'I2C esclave côté microcontrôleur), un seul bus (`I2C(0)`, `I2C(1)` accepté comme alias, `SoftI2C` alias de `I2C`), SCL/SDA au choix parmi `GP0`-`GP7`, fréquence bornée à 1 kHz - 1 MHz, 256 octets au plus par transaction. Pas de clock stretching (SCL tenue basse = `OSError(ETIMEDOUT)`) ni d'arbitrage multi-maître. Tirages internes du RP2040 non modélisés : il faut des résistances de tirage sur le bus (`usePullUp` d'un périphérique). Périphériques I2C (`Internal.PartialI2cDevice`) : comportement uniquement par script Python, au niveau transaction ; ils acquittent toujours adresse et octets écrits (pas de NACK sélectif), n'étirent jamais SCL ; au plus 4 adresses par composant. Cf. décision « Bus I2C électrique en drain ouvert ».
- Les 8 broches `GP0`-`GP7` sont **toutes** ADC-capables (contrairement au vrai Pico où seules `GP26`-`GP28` le sont) ; référence de conversion fixée à 3,3 V, codée en dur dans le shim Python (pas de paramètre `Vref` configurable, pas plombée sur `VOH`) ; pas d'échantillonnage périodique ni d'IRQ sur changement de valeur (le script interroge l'ADC à la demande), cf. décision « ADC (entrées analogiques) ».
- Le PWM (`machine.PWM`) est disponible indépendamment sur chacune des 8 broches `GP0`-`GP7`, sans modéliser le partage de canal de fréquence entre broches voisines du vrai RP2040 (« slices » matériels) ; `deinit()` repasse la broche en sortie numérique basse plutôt qu'en haute impédance, cf. décision « PWM (sorties modulées) ».
- Seulement 8 broches GPIO exposées (au lieu des 29 du Raspberry Pi Pico réel), en tableau fixe (pas de connecteurs activables individuellement). La LED embarquée (`GP25`, pilotable via `machine.Pin(25, ...)`) est un canal séparé, interne, sans connecteur électrique — elle ne compte pas parmi ces 8 broches, cf. décision « LED embarquée ».
- Le script Python doit être fourni via un fichier externe (chemin `.py`) ; pas de script inline en paramètre pour cette version.
- `libraryPath` ne désigne qu'**une seule** bibliothèque partagée (via un fichier `.py` de son dossier, faute de sélecteur de dossier natif dans l'annotation `Dialog` de Modelica) ; pas de sélecteur de dossier ni de liste de plusieurs bibliothèques, cf. décision « Import de modules auxiliaires ».
- Une seule instance de microcontrôleur par simulation (pas de multi-instances).
- Aucune protection contre un script qui ne rend jamais la main (boucle infinie sans appel à une API du shim) : la simulation peut rester bloquée dans ce cas.
- Windows uniquement (v0 développée et testée sous Windows 11 ; l'implémentation C utilise des API Windows pour le threading — non testé, probablement pas fonctionnel tel quel sur Linux/macOS).
- `pull` (résistance de tirage interne, paramètre du constructeur `Pin`) accepté pour compatibilité d'API mais sans effet électrique — pas de pull-up/pull-down réellement modélisé en v0.
- Les tracebacks affichés en cas d'erreur du script montrent `<string>` comme nom de fichier plutôt que le vrai chemin du script (limitation du mécanisme de gestion d'erreur retenu, cf. décision « Comportement en cas d'exception »).
- Les binaires de la distribution Python embarquée (quelques Mo) sont committés directement dans le dépôt git.
- `PyRuntime_destroy` ne joint pas proprement le thread worker ni n'appelle `Py_FinalizeEx` (repose sur la fin du process OS à chaque run de simulation, cf. décision « Mécanisme d'exécution »).
- `Pin.irq()` : tout callback tourne « soft » (déféré au prochain point de réveil du worker) — `hard=` accepté mais sans effet, aucune notion de contexte d'interruption matérielle dans ce modèle mono-thread. `machine.Timer` : pool fixe de 4 minuteurs (`MAX_TIMERS`), période minimale 1 ms (`TIMER_MIN_PERIOD`, garde-fou contre une tempête d'événements à durée nulle). Une exception levée dans un callback IRQ/Timer arrête toute la simulation (même politique que le script principal), pas d'isolation « le callback plante mais le reste continue ». Cf. décision « Interruptions sur broche et minuteurs logiciels ».
- `machine.Display` : un seul périphérique d'affichage pédagogique, écriture seule (pas de réception, pas un vrai protocole UART/Serial), liaison logique unique (`Display0` côté `MCU`), livraison instantanée du message entier (pas de bauds simulés), message tronqué à 128 caractères (`DISPLAY_MSG_MAX_LEN`). Liaison modélisée comme un connecteur logique causal (`Interfaces.DisplayLinkOutput`/`DisplayLinkInput`), pas électrique. Le texte reçu par `Peripherals.Display` s'affiche à la fois dans le journal de simulation (`Streams.print`, texte complet) et sur l'icône elle-même, fidèle à un vrai afficheur 20×2 : 20 premiers caractères du message courant en ligne 1, ancien message décalé en ligne 2 à chaque nouvelle réception (`Internal.StringToCharCodes` + `DynamicSelect` par colonne — contournement de la non-storabilité des `String`, cf. décision « Périphérique d'affichage pédagogique »). Écran de couleur fixe (pas d'animation lumineuse, le texte suffit). Jeu de caractères de l'icône limité (~69 caractères usuels), au-delà un caractère non reconnu s'affiche comme un espace. Cf. décision « Périphérique d'affichage pédagogique ».

## Vérification de la v0

*Scénarios concrets et critères de succès permettant de dire que la v0 « marche ». Chaque scénario teste une décision de la section « Choix architecturaux ».*

**Moyen d'exécution retenu** : chaque scénario est écrit comme un script OpenModelica Compiler (`.mos`), exécutable en ligne de commande via `omc <scénario>.mos` — reproductible et scriptable indépendamment de cette session (portable vers une éventuelle CI plus tard). Pendant le développement interactif, ces mêmes scénarios peuvent aussi être rejoués via les outils MCP-OpenModelica déjà connectés (`simulate`, `plot`, `getSimulationResultVariables`, `checkModel`), sans réécrire de script à chaque itération. Les scripts `.mos` (`verify_0X_*.mos`) et les modèles `MicroPythonMCU.Examples.*` correspondants vivent dans `Resources/Verification/` et `Examples/` ; chaque `.mos` s'exécute avec ce dossier comme répertoire courant (ex. `omc verify_01_basic_blink.mos`) et affiche `PASS`/`FAIL`. Note technique : le scripting `omc` n'a pas de fonction fiable de recherche de sous-chaîne (`Modelica.Utilities.Strings.find` et `System.stringFind` inexistants dans cette installation, accès aux champs d'un `SimulationResult` échoué également indisponible) — `verify_04` détecte donc l'échec attendu via `getErrorString() <> ""` plutôt qu'en cherchant le texte de la trace.
